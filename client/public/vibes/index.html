The Dr. Bartender Manual: Vibe Coding and the Claude Toolbox

Plain English, everything explained, every rule with its why.

You are already doing this job. You have shipped features, fixed things on the spot, and you run half the office. This manual is not here to introduce you to the work; it is here to give you the deeper education: what the machinery actually is, why the rules exist, which room each kind of work belongs in, and how much more you can ask for than you probably realize.

It is two books in one cover.

00 Before Everything: The Two Truths ▶

Truth 1: Almost nothing on the code side can break anything

You run this business's inbox, its money, and its admin panel every day; nobody needs to tell you it's real. What you need is the map of where "real" actually connects to the code side, because it is much smaller than it feels.

Exactly three things reach the live world: a push (always coordinated with Dallas first), direct edits to the production database (Dallas's), and destructive commands that you would have to approve by hand (anything with force, reset --hard, rm). That's the whole list. Everything else in Book One (thinking, planning, asking, editing, committing, building in lanes) happens in a sandbox with a save system underneath it, and cannot touch a client, a payment, or a paycheck.

So the posture is not caution. It is freedom: explore hard, build things, break things inside lanes, ask endless questions. The hot buttons are few, clearly marked, and none of them fire by accident.

Truth 2: You can literally just ask

Here is how this whole operation started. Dallas was not a programmer. He typed questions into claude.ai. Then he got the desktop app. Then he opened an old Windows PowerShell window, and every time something felt foreign he said: "Hey Claude, how do I do this thing? Give me step-by-step instructions for setting up this foreign thing called GitHub." And now here we are: a custom software platform running a whole company, built exactly that way, one honest question at a time.

That is the method. Not a fallback, not a beginner crutch: the method.

  • Confused by a word? Ask Claude to explain it like you have never coded.
  • Something feels wrong or scary? Say "stop, explain what's happening."
  • Want to do something and don't know how? Ask for step-by-step instructions and follow them.
  • Wonder if something is even possible? Ask. The answer is yes more often than you'd guess.

This is a POWERFUL tool. It does not judge, it never gets tired of questions, and it gets better the more context you give it. The rules in this manual are guides Dallas set up, each one a lesson learned the hard way, and each one comes with its why so you understand it instead of just obeying it. If a rule ever seems to be in your way and you don't understand why, don't silently work around it: ask Claude to explain it, and if it still seems wrong, tell Dallas. That is exactly how the rules themselves got made.

01 The Machines and Your Commute ▶

Where the work actually happens

All the real work happens on one computer: a Linux machine called the DRB-Mainframe that sits in Dallas's office in Chicago and never turns off. It has no monitor, no keyboard, no mouse. A computer like that is called headless: a powerful engine running in a locked room. Everyone connects to it remotely, works on it together, and leaves it running.

Your commute (two hops)

  1. Chrome Remote Desktop into the Windows box in Dallas's office. That gives you a full Windows desktop, as if you were sitting at it.
  2. From that Windows desktop, open a terminal (PowerShell or Windows Terminal) and SSH into the Mainframe.
ssh drbartender@<address Dallas gives you>

SSH ("Secure Shell") turns your terminal into a direct line to the Mainframe. When the prompt changes to drbartender@DRB-Mainframe:~$, you have arrived. From that moment, everything you type happens on the Mainframe. The Windows box is just the hallway you walked through.

Keep the geography straight, because it matters in Part 2:

  • The Windows box is where the Claude desktop app lives (Book Two).
  • The Mainframe (through SSH) is where the code, the repo, and Claude Code live (Book One).

You can open several terminal windows at once; each is a separate conversation with the same machine. Dallas usually has a few going. Normal and safe.

Terminal survival commands

You rarely type commands yourself (Claude does that part), but know these:

02 Which Claude, Which Room ▶

You have several Claudes available, and they are all the same brain in different rooms with different toolbelts. Using the right room is the single most important habit in this manual, and it is the one place you have been stumbling, so let's make it unmissable.

Room 1 · Claude Code, in the terminal, on the Mainframe
The workshop. It can see the entire codebase, the rulebook, the build board, the lanes, the review agents, the database, and the dev server. Every piece of work on the Dr. Bartender app happens here. All of it. Including the very first sentence of a new idea.
Room 2 · The Claude desktop app (Cowork), on the Windows box
The office. It is connected to the business side: the contact@ email, the calendar, Drive, Notion, Canva, Stripe. It is where you act as Dallas (Book Two). What it can NOT see: the Mainframe, the repo, the rulebook, or anything in Book One. (claude.ai in a browser tab is this same room in different clothes.)
Room 3 · claude.ai/design, in the browser
The art studio. Used only in the middle of a project, to design new screens, with a prompt written in Room 1 (Part 10).

The room test (one sentence)

Is this about the Dr. Bartender app: its code, its screens, its data, its behavior? Then it happens in Claude Code, in the terminal, on the Mainframe. Everything else about running the business happens in the desktop app.

The classic mistake, named out loud

The desktop app is right there when an idea strikes, and it will happily discuss a new feature, plan it, even write code for it. It feels exactly like working. It isn't. The desktop app cannot see the repo, so anything it builds is an orphan: not on main, not reviewed, not connected to anything real. The thinking gets stranded in a chat window instead of becoming a committed spec.

Signs you are in the wrong room:

  • There's no drbartender@DRB-Mainframe prompt anywhere in sight.
  • You ask Claude to open docs/build-board.md and it can't.
  • It's writing code but can't run the app or the tests.

What to do when you catch it: stop, copy out any thinking worth keeping, walk your fingers to the terminal (CRD, SSH, cd ~/projects/os, claude), and restart the conversation there with "let's work on ..." Two minutes of commute, and now the work is real: it lands on main, gets reviewed, and ships.

Why even the first sentence belongs in the terminal: our workflow's core rule is that thinking becomes committed documents on main the moment it exists (Part 6). A brainstorm in the wrong room produces thinking that lives nowhere.

04 Meet Claude Code ▶

Vibe coding means: you describe what you want in plain English, Claude writes the actual code, and you steer, question, and approve. In the terminal, that's Claude Code. To start it:

cd ~/projects/os
claude

Always start from inside ~/projects/os. That is how Claude finds the rulebook, the project's custom review agents, and its memory of this codebase. Started from the wrong folder, it is an amnesiac.

Then just talk. Things worth typing any day of the week, all completely safe:

  • "Show me the build board and explain what each item is."
  • "Explain in plain English what server/utils/pricingEngine.js does."
  • "What did we ship in the last two weeks?"
  • "Walk me through what happens, step by step, when a client pays a proposal."

Claude reads the actual code and explains it. Asking questions is free and touches nothing. If an answer uses a word you don't know: "explain that like I've never coded before." (Truth 2. It's always Truth 2.)

Permission prompts

Claude will sometimes stop and ask permission before running a command. Rules of thumb:

  • Reading files, searching, listing folders: always fine.
  • Editing files and committing, when it's the work you asked for: fine.
  • Anything containing force, reset --hard, clean, rm, or delete, or anything Claude itself flags as destructive: stop, screenshot, ask Dallas.

When in doubt: don't approve, ask. Nothing is ever lost by waiting.

05 Git, in Plain English (Including "What Is Main?") ▶

Save points

Git is the save system for our code. Think of a video game:

  • A commit is a save point: a permanent snapshot of the code at one moment, with a note about what changed.
  • The repository ("repo") is the whole memory card: every save since the project began. Our repo is the os folder.
  • GitHub is the cloud backup. The master copy lives there, safe even if the Mainframe caught fire.

Once work is committed, it is essentially impossible to lose. This is why you can relax.

Branches, and the answer to "what is main?"

A branch is a named timeline of commits. Git lets a project run many timelines at once, like parallel universes of the same code, so different pieces of work can proceed without colliding, then be combined (merged) later.

Every repo has one official timeline that all others eventually flow into. By convention it is named main. So:

Main is not a place or a folder. It is the official timeline of the code. "On main" means "part of the official version." Everything else is a draft universe that either gets folded into main or thrown away.

And the part you actually asked about, "how do I get there":

You are always already there. The os folder is permanently parked on main. You never switch it, never "go to" main, never leave it. Standing in ~/projects/os IS being on main. Type git branch --show-current there and it will say main. It will always say main.

That is deliberate, and it leads to the most important mechanical rule in the shop:

The big rule

The os folder never leaves main. Never run git checkout, git switch, or git checkout -b inside the os folder. If you ever see Claude propose one there, say no.

Why: the os folder is one shared workspace. You, Dallas, and several Claude windows are all looking at the same physical files at the same time. A folder can only be on one branch at a time, so if one window switches branches, every other window is silently dragged along, and their work gets stranded. This really happened once; a single git switch yanked a parallel window onto the wrong branch and nearly lost a plan. There is now a robot guard (scripts/guard-os-main.sh) that blocks commits if the folder somehow ends up off main, but the guard is a seatbelt, not an invitation.

"If we never leave main, where do branches happen at all?" In lanes. That's Part 6.

Push: the most serious word in Book One

  • Push = upload our commits to GitHub.
  • In our shop, push = deploy. The moment commits land on GitHub's main, robots ship the backend to Render and the frontend to Vercel automatically. Minutes later the change is live, in front of real paying clients.

There is no separate publish step. Push IS the publish button. Therefore:

You can push. Merging and pushing are the two moments you sync with Dallas first. A quick message is all it takes: "X is merged and ready, pushing unless you say hold." Why these two moments: a push ships EVERYTHING sitting on main, not just your work. Dallas may have commits parked there that he isn't ready to ship, and parallel windows merge work you don't know about. Coordinating first means nobody's half-done batch rides along by surprise.

Two mechanics protect you here:

  • The cue words are live triggers. Claude treats "push," "deploy," "ship it," and "send it" as the real deploy signal, so only say them when you mean them and you have synced with Dallas. Claude will never suggest pushing on its own: after a commit it goes quiet, and that silence is the system working, not Claude being stuck. Committed work sits on main, safe and unshipped, until someone gives a deliberate cue.
  • The cue starts a gate, not a launch. On the cue, Claude announces the batch ("N commits / M files pending. Run review + push?"), waits for an explicit yes, runs the full review fleet over everything going out, and only then pushes. Watch this sequence a few times before you run it yourself.

Words you'll hear constantly

Word Plain meaning
stageMarking specific files as "include these in the next commit." Claude stages by name, never "everything."
mergeFolding one branch's commits into another.
squash mergeFolding a whole branch in as ONE tidy commit. Clean final draft handed in, scratch paper shredded.
merge conflictTwo timelines changed the same line differently; someone must decide which wins.
revertUndoing a pushed commit the safe way: a new commit that reverses it. History is never rewritten, only extended.
06 How We Actually Work: Think on Main, Build in Lanes ▶

Say it like a motto: thinking lives on main, code is built in lanes.

Thinking lives on main

All brainstorming, specs, and plans are written as Markdown documents and committed straight to main, immediately, in the shared os folder:

  • Specs (what we're building and why) go in docs/superpowers/specs/. A real one: 2026-07-25-service-extension-design.md, the design for letting a client extend their bartender's hours mid-event and pay on the spot.
  • Plans (the step-by-step build instructions) go in docs/superpowers/plans/.

Why commit thinking instantly? An old wound: plans used to be written on side branches, and when a branch died, the thinking died with it. Hours of problem-solving, gone. Now nothing valuable ever sits anywhere except main, so nothing valuable can be stranded. (And now you know the deep reason projects must start in the terminal: a brainstorm's whole purpose is to become a committed document on main.)

Since thinking is just writing documents, any number of people and Claude windows can plan at the same time in the shared os folder, each in its own document. Planning never collides.

Markdown (.md), while we're here: plain text where # means heading and **text** means bold. Readable by humans and AI alike, no Word required. This manual is a Markdown file.

Code is built in lanes

When a plan is approved and it's time to write code, Claude creates a lane: a temporary, disposable copy of the codebase in a separate folder (under ~/projects/worktrees/, next to os, not inside it) on its own branch. Git calls the mechanism a "worktree"; we say lane because that's what it's for: one piece of work travels down it, then it closes.

The lifecycle, entirely Claude-managed:

  1. Cut: Claude creates the lane as a fresh copy of current main.
  2. Build: Claude writes code there, saving messy checkpoint commits as it goes. A lane is a sandbox; nothing in it can touch main or the live site.
  3. Review: agents check the lane's work before anything merges (Part 8).
  4. Merge: the lane is squash merged into main as one clean commit, through scripts/merge-lane.sh, which holds a real lock so two lanes can never merge at the same instant. (When you're the one driving the project, give Dallas a quick heads-up before the merge lands; see Part 5.)
  5. Delete: the lane is cleaned up, after triple-checking every change made it to main.

You never create, name, visit, or clean up a lane. Curious what's in flight? Ask Claude to "show lane status," or read the build board.

Why lanes? A half-finished or broken build can never hurt main. Worst case, a rotten lane gets thrown away and re-cut from the plan, which is safe on main. The expensive thing (thinking) is never at risk; only the cheap thing (mechanical code Claude can redo) is.

The two tracks: how every task starts

Every task is one of two sizes, and you pick the track by how you open your sentence:

Track 1 · Quick fix

Small, obvious, low-risk. Typo, color, label. Edited right on main, committed, done. No lane.

Magic phrase: "Just fix this real quick: ..."

Real example: our menus only ever list Athletic Brewing as the non-alcoholic beer (house rule, never Heineken 0.0). Spot a stray "Heineken 0.0" in menu copy? "Just fix this real quick: the NA beer on the classes page should say Athletic Brewing." Claude edits, shows you, commits. Two minutes, and it sits safely on main until the next push.

Track 2 · Project

A real feature: new behavior, new screens, anything touching money or multiple parts of the system. Full road: brainstorm, spec on main, plan on main, review the plan, build in a lane, review the lane, merge.

Magic phrase: "Let's work on ..."

Real example: "Let's work on letting clients extend their event by an hour and pay on the spot" became the service-extension spec, a five-lane plan, and shipped 2026-08-04. The reviews along the way caught two real money bugs before they ever reached main.

Not sure which track? Ask. Claude will tell you, and it errs toward project when money is anywhere nearby.

The build board: the shop's whiteboard

docs/build-board.md is the one-page index of all work, in three sections:

  • Ready to build: plan written and reviewed, waiting for a go.
  • In flight: a lane is open right now.
  • Recently shipped: merged and pushed, newest first.

Each line links to its spec and plan. Claude maintains it as a byproduct of working; humans read it, never edit it. It is the fastest answer to "what is going on right now?"

07 How to Talk to Claude (This Is the Real Skill) ▶

Brainstorming style, house rules

  • Prose, one question at a time. Design talk is a conversation, not a form. Claude digs in, forms an opinion, and leads with it; you two hash it out one question at a time. If Claude ever gives you a multiple-choice menu during design talk: "no menus, just talk to me."
  • Short answers are real answers. "yes," "looks good," "do that" are firm decisions, and Claude treats them as final.
  • Approvals are section by section. On a big design you approve each piece as you discuss it, and those little approvals ARE the approval. No end-of-spec re-reading ceremony. When the last section is agreed, the spec is done.
  • Don't rubber-stamp, and don't be rubber-stamped. If you don't understand, say so; making Claude explain is productive work. If you think Claude is wrong, push back. It's instructed to give real analysis, not flattery. Give it the same.

Effort levels

Claude thinks harder when asked, and we ask deliberately:

  • "Use maximum reasoning effort": whenever the work touches real money, login/security, or the database's shape. Examples: anything near pricingEngine.js, Stripe or payments, server/middleware/auth.js, schema.sql, or anything that ripples across layers.
  • Normal effort: one-file tweaks, copy, CSS, docs.
  • The house test: "If this were subtly wrong, would the bug be hard to catch?" Yes = max effort. Instantly obvious on screen = normal.

08 The Safety Nets (Reviews) ▶

We do not trust any single pass of work, human or AI. Layers of independent review agents check everything, scaled to how dangerous the change is.

The sensitive-paths list

scripts/sensitive-paths.txt is the single master list of every file where a mistake means lost money, broken security, damaged data, or a wrong message to a real person. pricingEngine.js is on it. The Stripe webhook handlers. auth.js. schema.sql. The refund code. The email and SMS senders.

The rule: any change touching any file on that list gets the full review fleet, no matter how tiny it looks. Everything else gets a lighter look plus a sweep before push.

Why so paranoid · a true story

A file that handles client drink-plan submissions could write to a money column, but it wasn't on the list yet. A change to it got the light review, and the bug it carried overbilled a real client by $627. He was refunded, the file went on the list, and the lesson went into this manual: sensitivity follows the code. When Claude says "this touches a sensitive path, running the full fleet," that is the shop remembering Jack.

The review layers

  • Design-stage (before any code): "review the spec" runs three agents that check a spec against reality, hunt gaps, and probe risk; "review the plan" runs three more that check the plan matches the spec, splits sanely into lanes, and is buildable.
  • Per-lane (before any merge): agents review the lane's changes. This gate caught the two service-extension money bugs.
  • Push-time (before anything goes live): a sweep of everything since the last push, checking the seams where separate pieces of work touch, plus a fresh full-fleet pass on anything sensitive, plus the rival reviewers on sensitive pushes.
  • The iron rule: a review agent that crashed, stalled, or came back vague counts as a FAILURE, never a pass. A blind spot is not a green light.

The rival reviewers: Codex and Gemini

Two AI models from rival families live on the Mainframe as command-line tools: Codex (OpenAI) and Gemini (Google). In our shop they have exactly one job in Book One: second opinions. They are reviewers, never builders. Claude leads; they advise.

How it works: inside Claude Code, "get a second opinion" (the /second-opinion command) hands the changes to Codex and Gemini in parallel. They hunt for problems independently. Then, and this is the important part, Claude checks every finding against the actual code before showing you anything, because raw rival-model output is noisy and many findings don't survive contact with reality. Only verified findings surface. The same machinery fires automatically at push time whenever a batch touches sensitive paths. There is also /gemini-spec for a rival read on a spec document.

The why is a story: different model families have different blind spots, so decorrelated eyes catch what one family misses. Codex once caught a real money bug in the staffing roster that the entire Claude fleet had passed, and later a shift-handling blocker in the event-details work, both before they shipped. The value is not that the rivals are better. It's that they are different.

Three laws about them:

  1. Their findings are verified, never obeyed. A wrong finding is discarded without apology.
  2. Their failure never blocks anything. If Codex's quota is out or Gemini's billing hiccups (both happen; they run on prepaid accounts), Claude reports it and the Claude fleet remains the gate.
  3. You never drive them directly. They only run through Claude Code's commands. Your job is understanding what you're watching: "Codex flagged X, verified real, fixing" versus "Gemini flagged Y, checked it, false alarm."

Ask for the review out loud, every time

Reviews are supposed to be baked into the workflow, and mostly they are. Ask anyway. House habit, not an insult to Claude:

  • Spec and plan reviews only run when someone asks. Deliberately not automatic. When a brainstorm settles into a spec: "review the spec." When a plan is written: "review the plan." If you don't say it, it may not happen.
  • Lane and merge reviews are automatic, but you verify them. Before any merge: "What review level ran on this, and what was the verdict?" Claude must state which level ran (light look or full fleet) and what was found. A vague answer is a red flag, not a pass.
  • Asking twice costs nothing. A skipped review is how a $627 bug reaches a real client. "Did the review run?" is never an annoying question here.

One boundary: the big push-time review runs only on a real push cue, never early. Ask freely about spec, plan, and lane reviews; don't ask Claude to pre-run the push-time fleet "just to be safe." That one has its own moment.

09 Money and Data Rules (Know These Even If You Never Touch Them) ▶
  • Everything is connected. House rule: if you change X, find everything that depends on X and update it too. Example: if a proposal's price changes, its payment status must be re-checked, because "Paid in Full" at the old price isn't paid in full at the new one. Claude checks these ripples automatically; never tell it "skip that, just change the one thing."
  • Business rules live in the code, and they are exact. Example: hosted packages include one bartender per 100 guests in the price; bartenders beyond the ratio bill hourly plus a gratuity surcharge. Rules like that are law in pricingEngine.js. When a client-facing answer depends on a rule like this, have Claude check the code instead of anyone's memory. The code is the truth.
  • Watch for unit traps. Most money is stored as integer cents ($100 is stored as 10000), but proposals store dollars, for historical reasons. You don't memorize which is which; you remember that traps like this exist, which is exactly why max effort and the review fleet exist.
  • Hands off production services. Using admin.drbartender.com is your normal job, always fine. Directly editing the live database, the Stripe dashboard, or Render/Vercel settings is Dallas-only.
  • The dev server (the test copy of the app on the Mainframe) is a Claude-managed background process and does not restart itself when server code changes. Change not showing up? "Restart the dev server."
10 Building Screens (The Design Round Trip) ▶

Any part of the app a person sees and touches (a page, a form, a dashboard) we call a surface. Claude Code is superb at logic and wiring, but for designing how a brand-new surface looks and feels, we use the art studio: claude.ai/design.

When to make the trip (and when not to)

  • Go to the studio: a brand-new surface, or a heavy visual redesign of an existing one.
  • Stay in the terminal: everything else. Layout fixes, new fields on an existing screen, styling tweaks, ordinary UI work. Terminal Claude does those directly against our existing CSS. Most UI work never leaves the terminal.

The design systems (why the studio output looks like our app)

On claude.ai/design we keep design-system projects: our real colors, fonts, and components, extracted from the live product, so the studio designs with our actual skin instead of generic AI-pretty taste.

  • Dr. Bartender OS Design System: the admin console and staff portal. Two themes: After Hours (dark) and House Lights (light).
  • Apothecary Design System: the public marketing brand (the parchment-and-serif look).

Design a surface inside the matching project. The design system is what carries the rules, which is why the next step works.

The trip out: a lean prompt, cut and paste

In the terminal, mid-project, tell Claude Code to write a design prompt for the new surface. The good kind of prompt is lean: what the surface is for, who looks at it, what data it shows, and the paths to the existing screens and components it should feel adjacent to. Paths and descriptions, not a rulebook. (The design system already IS the rulebook; a prompt stuffed with strict rules just fights it and gives worse results. We learned this by comparing outcomes.)

Copy the prompt from the terminal chat, paste it into the right design project in your browser, and iterate there until it looks and feels right. This part is genuinely fun, and iterating is free: ask for variations, push on spacing, change your mind.

You may see old docs/*-design-prompt.md files in the repo (potion-planner, payroll-screen, recipe-card). Those are the previous era's method, when the prompt had to carry everything. History, not the pattern to copy.

The trip back: the design connector (no more zip files)

When the screen is right, go back to the terminal and tell Claude Code to pull it in. Claude uses the design connector (a tool called DesignSync) to list and read the files straight out of the design project. No downloading, no zip files, no ferrying.

Then terminal Claude does the part that makes it real: wiring. Swapping fake data for real endpoints (through utils/api.js), folding styles into index.css, adding the route and auth guards in App.js, and putting the work through the normal lane-and-review machinery like any other project code. The studio decides how it looks; the terminal makes it true.

One setup note: the design connector rides a claude.ai login in the terminal session. If Claude ever says it can't reach the design project, that's an authorization thing, not a you thing: ask Claude how to fix it (it's a one-time /design-login), or ask Dallas.

11 When Something Goes Wrong ▶

It will, and it is almost never a big deal. The system is built so mistakes are cheap.

Red text is not an emergency. Error messages are information, not damage. Copy the message to Claude, ask "what happened?", and nine times out of ten it's fixed in the next message.

The unbreakable habit: when unsure, stop and ask. Nothing here is ever harmed by pausing; things are only harmed by forcing forward.

  • Claude asks permission for something you don't understand: screenshot, send to Dallas, wait.
  • A merge conflict on a sensitive path: Claude stops on its own. Let it. That one is Dallas's call.
  • A push fails: the rule is stop and report. Never retry with force. A failed push is always safe; a forced one is not.
  • You think you broke something: you almost certainly didn't. Committed work is essentially indestructible, and uncommitted work is protected by rules that stop Claude from destroying anything without explicit approval. Say "stop," then tell Dallas what happened. Honestly reporting a mistake immediately is a core house value. Zero penalty, every time.
What actual danger looks like: approving commands with force, reset --hard, clean -f, or rm; pushing without having synced with Dallas; editing the live database directly. All three require you to actively do something. Don't, and you're safe.

C3 House Style for Anything a Client Reads ▶

When you draft words that leave the building (emails, texts, social captions, site copy), a few house laws apply:

  • No em dashes in client-facing copy. Use commas, colons, or a period and a new sentence. (You'll notice this manual practices it.)
  • Email over SMS by default. Every text message costs real money; email is effectively free. Texts are for genuinely time-sensitive things.
  • Only claim what's true. The NA beer is Athletic Brewing, never Heineken 0.0. And any time copy depends on how the product actually behaves ("you can reschedule anytime!", "tips go 100% to your bartender"), verify against reality first. The code is the truth, and the terminal is where the truth lives: if you're unsure, ask terminal Claude to check before the copy ships.
C4 Making Images ▶

You do the social posts, and Dallas has been generating art for the blog. Same rig is available to you, and this is one Book Two purpose that happens in the Book One room, because the image tools, keys, and upload path all live on the Mainframe.

The rig

  • gpt-image-2 (an OpenAI image model) is the house standard. It won a head-to-head against Google's image models for our use: better style match, and it renders text baked into the image cleanly instead of producing alien scribbles.
  • Gemini's image models are the alternate: cleaner and more minimal when that's the look you want.
  • Either way, you don't touch any of that machinery. You describe; Claude drives.

The recipe

In the terminal (cd ~/projects/os, claude):

  1. Say what it's for and what it shows. "Generate a square image for an Instagram post about summer cocktails: the apothecary chalkboard style, one concept, a copper mug with a thermometer, chalk line art, teal accent."
  2. Claude generates, then hands you a link. It converts the image to web-friendly weight and uploads it, and you open the link in your browser to judge it. (Generated files get shared by link because that's the established review path.)
  3. Iterate freely. "Warmer," "less clutter," "make the text bigger," "try a version without the border." Each round takes a couple of minutes. Regenerating until it's right is normal, not wasteful.
  4. Download the winner and use it in the post.

The house look (a default, not a law)

Blog art follows a codified style called apothecary chalkboard: dark charcoal blackboard background, white chalk line art, selective teal, warm-orange, and lime accents; covers are square with a condensed uppercase title and a row of labeled icon tiles; inline images are one concept with a small handwritten caption. Social art should follow the same look for now, so the feed and the blog feel like one brand.

But hear this the way Dallas means it: we aren't making rules here. If you or Dallas wants something else for a particular post, prompt for something else. The style is a default that keeps things coherent when you don't have a reason to deviate, not a fence.

One brand note: the chalkboard look belongs to the client-facing side of the house (the blog, social, the public brand). Admin-side things (the console, internal tools, internal docs) wear the OS skin instead. Art follows the brand of the surface it lands on.

One real boundary to know: the marketing site's photos are real photographs, deliberately. Generated art is for the blog and social graphics; it does not replace the real photos of real events on drbartender.com.

C5 Carrying Work Between the Books ▶

The two rooms meet constantly, and the skill is noticing which book a thing belongs to while you're in the middle of the other one.

Ops work uncovers an app problem. You're in the inbox and a client says the payment page errored. Or you notice the admin panel has no button for a thing you do weekly. That is Book One work wearing Book Two clothes. Don't ask desktop Claude to fix it (it can't); carry it across the hall: terminal, cd ~/projects/os, claude, then "just fix this real quick: ..." or "let's work on ..." You've already done this, and fixing a thing the moment it has no path in the admin panel is exactly the muscle. The only correction from history: start that work in the terminal, not in the desktop app.

Dev work needs an ops action. A project needs an email sent to a client, a calendar hold, a decision about how a client relationship should feel. That's Book Two (or a conversation with Dallas). The terminal codes; the office communicates.

When you're not sure which book something is: the room test, one more time. About the app's code, screens, data, or behavior: terminal. About clients, email, money moves, schedule, content: desktop app.
