# Running the OS on the dev box

How the servers and the tests actually run here. Every "how to" line below was run on 2026-10-20 from a lane worktree unless it says "from memory, not re-run on 2026-10-20". Facts that were only read (a memory, a config file) say so.

## The backend

- Start it from the repo root (or a lane root) with `node server/index.js`. It is a plain Node process with no reload: after any server-side edit, stop it and start it again. Run on 2026-10-20 on port 5002.
- `.env` sets `PORT=5000` and `NODE_ENV=development`; override the port on the command line (`PORT=5002 node server/index.js`) when 5000 is another window's. `.env` is gitignored and a lane gets it as a symlink from `npm run worktree:new`.
- Wait for these two lines before using it: `✓ Database schema initialized` then `✓ Server running on port <PORT>`. On 2026-10-20 they arrived about 30 seconds after launch. A third line, `[schedulers] disabled: NODE_ENV='development' is not 'production'`, confirms no scheduler and no real send will fire.
- `initDb()` applies `schema.sql` idempotently on every boot, so a restart also applies schema changes.
- The CORS gate: `server/index.js` allows `CLIENT_URL` (or `http://localhost:3000`) always, and any `http://localhost:<port>` or `http://<name>.localhost:<port>` only when `NODE_ENV` is exactly `development`. Settled by running it on 2026-10-20: with `.env` loaded, a client on port 3002 and `staff.localhost:3002` both got `Access-Control-Allow-Origin`; with `NODE_ENV=staging` on the command line they got a 500 and no header while `localhost:3000` still passed. So `NODE_ENV=development` on the command line is redundant when `.env` is present and necessary only when the environment overrides it; the memory that said to always pass it was describing the override case.
- The backend is Claude's process, not Dallas's (his words, 2026-05-17: it is a you thing). Start it and stop it yourself, by the pid listening on the port.

## The client

- Start it from `client/` with the flags on the command line, never in `client/.env`: `PORT=3002 HOST=localhost DANGEROUSLY_DISABLE_HOST_CHECK=true BROWSER=none REACT_APP_API_URL=http://localhost:5002 npx react-scripts start`. Run on 2026-10-20: `webpack compiled with 1 warning` after 57 seconds (the warning is a missing source map in a dependency, `html2pdf.js`, not our code), and the page answered 200 on port 3002.

- Host contexts without code changes: `localhost:<port>` is admin, `public.localhost`, `staff.localhost` and `hiring.localhost` are the other sites (`getSiteContext()` in `client/src/App.js`). From memory, not re-run on 2026-10-20.

## The two-hour limit

- A background process started through the harness stops at the two-hour cap and must not be restarted on the same call. For a browser gate, start the API and the client inside the same foreground command as the checks and stop them in a trap at the end, by the pids listening on their ports. Never `pkill -f <pattern>` when the pattern is in your own command line: it kills your shell. From memory, not re-run on 2026-10-20.

## Running tests

- The server suites (`node --test <file>`) run against the shared Neon dev database, the same one every window's backend uses. Run them one at a time, never in parallel and never from a lane while another window runs a suite. From memory, not re-run on 2026-10-20.
- Read the pass count, not only the fail count. A suite without `require('dotenv').config()` dies silently (its DB tests fail `ECONNREFUSED` while the pure tests pass), so a green-looking run can be a dead suite. From memory, not re-run on 2026-10-20.
- Never `CREATE TEMP TABLE` through the pooled dev URL. The pooler runs in transaction mode and a temp table outlives the session and shadows the public table for every window. From memory, not re-run on 2026-10-20.
- The money smoke is `npm run test:smoke` (`scripts/testdb-smoke.js`): it resets the `ci-smoke` Neon branch from production, runs `initDb` against it, then runs `scripts/money-smoke-list.txt` serially. It needs the Neon key in the environment or in the key file under `~/.secrets/` that the script header names, and takes about eight minutes. Not run on 2026-10-20; read from the script header.
- Until the flip, `.husky/pre-push` runs `node scripts/push-gate.js verify`, which honours a receipt from `npm run gate` and otherwise runs the money smoke (when `server/` changed) and the exact Vercel client build (when `client/` changed). The client build has been OOM-killed beside a concurrent lane build (seen when the box had 3.2 GiB; on 2026-10-20 `free -h` reports 30 GiB). Wait for the other build rather than `--no-verify`.
- The ordinary suites run through the runner, `npm run run-suites -- --staged` (`scripts/run-suites.js`; or `-- --changed <base>..<tip>`, or `-- <file>...`; npm needs the `--`). The dev-suite lock serializes every run that goes through the runner (`npm test` and a plain `node --test` take no lock). Each suite runs under GNU coreutils timeout (`gnutimeout` on this box, whose `timeout` is uutils and kills only its direct child; the runner refuses to run without a GNU one), which at 180 seconds kills the suite and every process in its process group; after each suite the runner kills whatever the suite left in the run's session outside that group (one stderr line when it does). A child that leaves the session too (`setsid`, Node's `detached`) survives the bound, that sweep and a signal to the runner and runs unlocked, a stated limit. Each suite's log under `drb-review/_runs/` in the git common dir is its TAP record, written by Node's TAP reporter alone, and what the suite itself prints goes to a `.out` beside it; both are named for the suite's path with slashes as dashes plus 6 hex of the path's sha1, so two paths never share a name, and each `summary.json` entry names its `log` and `out`; the counts come from the summary block Node's reporter ends each log with (a `1..N` plan line, then `# tests`, `# pass` and `# fail`), so a `# pass` line anywhere else is no summary, and a suite with no summary, a fail, a cancelled test, a non-zero exit or a timeout fails the run. The run writes a `summary.json` there, an empty one when it reaches nothing. A `--log-dir` is one run's: a second run on it while the first lives, or a run on a dir holding anything the runner did not write, refuses in one line and leaves the dir as it was; a reused one loses its old summary and logs first thing, and a refusal after that (a missing file, git failing, no GNU timeout) is one line and writes a summary with one failure and `did_not_run` naming the reason. Run on 2026-10-20.
- The money smoke takes the smoke lock itself, so a review-time smoke and a gate never reset the `ci-smoke` branch under each other. `--dry-lock` takes the lock and exits without touching anything else; `--tap-dir <dir>` writes one TAP log per suite and a `summary.json`, which says `skipped: true` when no Neon key resolved and carries `did_not_run` with the reason when the smoke refuses after clearing the dir's old files; like the runner's `--log-dir`, it is one run's. With or without `--tap-dir`, each suite's tick is its TAP summary plus its exit, so a money suite that registers no tests or exits before its tests end fails the gate; without it the console shows Node's own report as before. Its suites and `initDb` run under the same GNU timeout as the runner. The dry lock, the no-key `--tap-dir` path and the suite runs on fixtures were run on 2026-10-20; the with-key path was not.
- Both print one line while they wait for their lock, and one line naming an override (`RUN_SUITES_ROOT`, `DRB_DEVDB_LOCK_FILE` or `DRB_SMOKE_LOCK_FILE`) when one is set. A signal to the runner or the smoke (Ctrl-C, `kill`) stops the whole run, a waiter and a running suite included, and frees the lock; a suite that ignores the signal is killed 5 seconds later. The locked run turns the signal into an exit once the suite in hand has returned, so the smoke's temp TAP witness (it can quote `ci-smoke` rows) and a run dir's marker never outlive it. A `kill -9` of the runner or the smoke is noticed before the next suite (the smoke also checks before the Neon reset and before `initDb`), and the run stops there. Each suite, and the smoke's `initDb`, holds the lock while it runs, so a `kill -9` of the locked run itself keeps the lock held until that suite ends rather than letting the next run start beside it, and a hung suite and its process group still die at the bound (`initDb` at 120 seconds), which frees the lock; the sweep after a suite is skipped then, so a child that left the group survives a `kill -9` of the locked run. The lock files (`drb-devdb.lock` and `drb-smoke.lock`) live in the git common dir and need no cleanup after a crash: flock releases when the last holder exits. Each of these was run on 2026-10-20 through the lane's tests, the signal to a running suite and the `kill -9` with a hung suite on the runner; the smoke's checks before the Neon reset and `initDb`, a signal or `kill -9` while a money suite runs, and the `initDb` bound sit behind the key and were not.

## Lanes and ships

- `lane:status` runs at every session start: the `SessionStart` hook in `.claude/settings.json` runs `node scripts/show-location.js && node scripts/lane-status.js --session-start`, which prints the flip marker's state, the gate and watch markers, the last ship (or the one in flight, an unsettled one, a watch to run again) and one line per stale lane, at most twelve lines, and always exits 0. `npm run lane:status` prints the same markers and ship lines ahead of the full lane report and exits 1 when a lane is stale. Run on 2026-10-23 from the session-status lane.
- A ship's log is `<git-common-dir>/drb-ship/<sha>.log` (from `os`, `.git/drb-ship/`), one `<ISO time> <stage> <text>` line per event, ending in at most one `result <ok|ok-no-push|refused|failed|pushed-elsewhere> <text>` line; a push whose outcome stayed unknown has none until a later run completes it. Beside it `<sha>.json` is the manifest `lane:status` reads (never the log's prose), `<sha>.watch.log` the post-ship watch's log, and `last` the sha of the latest ship started. Read from the step 3 plan, decision 6, and `scripts/lib/shipLog.js`.
- `npm run ship -- --status` prints the manifest's fields and the last fifteen log lines. It comes with the ship lane of step 3 and was not on main when this line was written; read from the plan, not run.
