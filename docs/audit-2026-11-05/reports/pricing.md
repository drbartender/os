# Pricing audit: how a price is computed, frozen, re-computed, compared and displayed (repo at 13f2645, 2026-11-05)

Summary
- Counts: 0 critical, 1 high, 2 medium, 3 low (6 findings; 4 CONFIRMED by end-to-end code trace, 2 CONFIRMED at the code level but with one step that depends on DB/UI state, marked where it matters).
- Worst: PRC-01. Comping a "Drink Plan Extras" invoice (`PATCH /api/invoices/:id` status void, default `reconcile_total`) lowers `proposals.total_price` but leaves `pricing_snapshot.total` and the `proposal_addons` row untouched, so the comped add-on is silently re-billed by the next re-price (any editor save, lab save or cancel-line), the proposal page and the client portal show different Totals in the meantime, and the create-intent election path charges the stale snapshot total.
- The engine itself is sound: every worked example below reproduces PRICING.md and the money laws (hosted 1:100 ratio with `isHostedPackage` on every bartender-cost path, the sub-100 surcharge, the $550 / 25-guest hosted minimum, per-type add-on math and the law-6 quantity shape, gratuity computed on top and never diluted, per-line and total rounding to whole cents). `node --test` runs: pricingEngine 39/39, addonQuantity 14/14, adjustmentRules 11/11 (pins the client twin), clientPriceLines 13/13, gratuityLabels 3/3 (pins the client twin), contractDuration 12/12, cancellationMath 11/11, foldDecision 2/2, bookingWindow 9/9, additionalTimeRate 9/9, changeRequests.gratuity 3/3, coverageEngine 9/9; the failures in invoiceLineItems (9), contractDuration.extension (14) and changeRequests (1) are all `ECONNREFUSED 127.0.0.1:5432` (DB-backed), not assertions.
- Frozen-rate posture (law 4) is as the law describes: the fold, the extension delta, the printed added-time rate and the submit/lab upserts read the live catalog; those are the documented open defects D0939/D0950/D1009/D1012/D1087/D1090/D1110 and are listed below, not re-reported. The one new freezing hazard found is PRC-01 (a `total_price` writer that leaves the snapshot behind).
- Overall posture: strong. Every client-facing write (switch, sign, change request, drink-plan submit) prices from row truth through the one engine, the client never supplies a stored total, `reconcileProposalPaymentStatus` follows every `total_price` write I could find, and the client/server twins (adjustmentRules, gratuityLabels, eventTypes, bundle config, filterAddons/visibleAddonsFor, recoverAddonQuantities/storedToInputCount) agree. The defects are at the seams: one `total_price` writer outside the engine, one preview that re-derives staffing, one pay-now charge helper that is not the engine, and display/doc copies.

### PRC-01 high CONFIRMED — Comping a Drink Plan Extras invoice lowers `total_price` only; the comped add-on survives in `pricing_snapshot` and `proposal_addons`, so the next re-price bills it again and the client surfaces disagree in between

The editor PATCH rebuilds the add-on set from `addon_ids` (crud.js:416-424), which the editor seeds from the row's `proposal_addons` (formState.js:6), prices through `calculateProposal` (:549) and writes `total_price = snapshot.total` (:565-569), then deletes and re-inserts `proposal_addons` (:668) and mints the delta (:800-801). Client submits the plan with a $100 per-guest add-on, pay-now: the fold writes `total_price` 110000 and `snapshot.total` 110000, a Drink Plan Extras invoice for 10000 is minted, the row is demoted to deposit_paid. (a) Immediately: the proposal page prints Total $1,100.00 and "remaining $100.00" (ProposalView.js:636-650 reads `snapshot.total`), the portal Prescription tab prints Total $1,000.00 (`total_price`), the next invoice rebuild folds a -10000 gap into the package line and pages Sentry `invoice_lines_unexplained_fold` on every rebuild. (c) If the comp lands while the proposal is still payable (a crafted drink-plan PUT is not gated on booked status: `drinkPlans.js:118`, `submit.js` has no status check) and the client then pays in full with a gratuity election, create-intent charges `effSnap.total` (stripeCreateIntent.js:111), i.e. 110000 plus gratuity, and the webhook writes `total_price` back to the stale 110000 plus gratuity (:256-262): the comp is undone at the moment of payment.
- Existing tests: `server/routes/invoices.extrasVoid.test.js` (DB-backed, could not run here) asserts only that `total_price` drops by the folded amount ("comp mixed add-on/bar/syrup: removes the FULL extras from total_price") and that the path-switch mode leaves it; nothing asserts the snapshot, the add-on row or a later re-price. `invoiceLineItems.test.js` pins the drift report that this state triggers. No test enshrines the re-bill; the comp test enshrines only the half that is correct.
- Proposed fix: make the comp a real line removal, not a `total_price` subtraction. In `voidExtrasInvoiceWithReconcile` (comp mode), delete the comped `proposal_addons` rows (the addon `source_id`s on the invoice's line items) and undo the bar increment, then run `foldExtrasIntoProposal` with Before = the rows as they stand and After = the rows without them (the cancel-line core already does exactly this; reuse `applyLineItemCancel` per line, or call the fold directly), so `total_price`, `pricing_snapshot` and `proposal_addons` move together and the next re-price cannot resurrect the charge. Consumers to update in the same change: `invoices.extrasVoid.test.js`, the comp confirm copy in the admin invoice UI, `submit.js` path-switch mode (must stay a pure void), `balanceInvoiceMonitor` if it reads the comped amount.

### PRC-02 medium CONFIRMED — The client-portal change-request preview re-derives bartenders from the ratio, so an admin's over-ratio bartender (and its surcharge and the gratuity on the crew) drops out of the estimate the client acknowledges
- Category: money-correctness / logic
- Location: `server/utils/changeRequests.js:106` (`numBartenders: proposed.num_bartenders ?? null`), `:150-160` (`buildPreview`); `server/routes/clientPortal/changeRequests.js:58-65` (calculate), `:116-125` (create: `acknowledged_total` must equal `price_preview.estimated_total`, stored at :137-141); `client/src/pages/public/portal/ChangeRequestForm.js:41-42` (the form sends guest_count, event_duration_hours, num_bars, package_id, never num_bartenders); the quote surface's own fix for the same hazard: `server/routes/proposals/optionsPricingShared.js:58-78` (`overrideOnlyBartenders`) and the comment at `server/routes/proposals/publicOptions.js:230-238`; the engine: `server/utils/pricingEngine.js:143-153` (`actual = override ?? required`).
- Reachable by: client (portal, logged in) and the admin who reads the stored `price_preview` on the change-request card.
- Evidence: `priceProposedState` passes `proposed.num_bartenders ?? null`, with no fallback to the stored column and no `overrideOnlyBartenders` strip/keep decision. The portal form never sends `num_bartenders`, so `calculateStaffing` gets `null` and prices `required` bartenders. The public options quote has the identical call shape and had to add `overrideOnlyBartenders` for this exact reason ("an admin staffing override would be silently re-derived from the 1:100 ratio and the quote would drop the extra-bartender charge AND the gratuity that rides on the crew size").
- Failure scenario (cents): BYOB Core Reaction, 40 guests, 4h, admin override `num_bartenders = 2` (a luxury second bartender): engine case B below, `total_price` 71000 (35000 base + 1 extra x 4h x (4000 + 5000 surcharge) = 36000). The admin card shows "current $710.00, estimated $350.00" for a request that changes no price; on approval the editor PATCH detects the override (`detectNumBartendersOverride`) and keeps 71000. With a paid client gratuity the gap widens by rate x 1 staff x hours. The stored consent (`acknowledged_total` 35000) does not match the approved price.
- Existing tests: `server/utils/changeRequests.test.js` (4 pure tests pass; the DB one fails ECONNREFUSED) and `changeRequests.gratuity.test.js` (3/3) cover the gratuity carry and allowlist; none covers a stored bartender override. Nothing enshrines the defect.
- Proposed fix: in `priceProposedState`, `numBartenders: proposed.num_bartenders ?? overrideOnlyBartenders(proposal)` (move `overrideOnlyBartenders` into `changeRequests.js` or a shared module so the quote, the switch and the change request share one rule), keeping `null` only when the stored value is a provable derivation. Consumers: the admin change-request card (`ProposalChangeRequestCard.js`) copy, the stored `price_preview.staffing.estimated`, and `buildDiff` (NUMERIC_FIELDS already includes num_bartenders).
- Verification: a pure test in `changeRequests.test.js`: proposal with `num_bartenders` 2, `pricing_snapshot.staffing = { required: 1, actual: 2 }`, no `num_bartenders` in `proposed`; assert `snapshot.staffing.actual === 2` and `estimated_total === current_total` for a no-op change.
