# Payouts audit (money OUT to staff) — Dr. Bartender OS @ 13f2645 (2026-11-05)

Summary (5 lines):
- Counts: 0 critical, 4 high, 4 medium, 5 low (13 findings; 11 CONFIRMED, 2 PLAUSIBLE).
- Worst thing: a manager (a role deliberately locked out of the payroll tier) can rewrite a contractor's Venmo / Cash App / PayPal handle and preferred method through `PATCH /api/admin/contractors/:userId/tip-page`, with no audit row, and those exact columns are what the admin's Pay panel builds the payout deep link from (POUT-01).
- Close behind: two post-completion roster paths (unassign, deny) leave a no-show's wage + tip line payable because they re-accrue only when an out-of-area bonus lock moved (POUT-02), and accrual's "prior line" lookup ignores the pay period, so a cross-period line can double a wage or zero it (POUT-03).
- Posture: the payroll core is careful and well-guarded (single payout INSERT path, single total writer, row locks on every admin money write, cumulative markers on claw/roll-forward, Chicago business day everywhere, bank PII encrypted and masked in every projection, no Stripe transfer path at all: staff are paid off-platform and the admin records it). The defects are at the seams: who may write the payout destination, which roster edits trigger re-accrual, and the period scope of accrual's prior-line lookup.
- There are no Stripe Connect transfers or payouts to staff: `payouts` rows are marked paid by an admin after an external Venmo/Cash App/PayPal/Zelle/check payment; `stripePayouts.js` / `stripePayoutSync.js` mirror the business's own Stripe balance payouts (admin/manager read-only), not staff money.

### POUT-01 high CONFIRMED — A manager can redirect a contractor's payout by rewriting the payment handles the admin Pay panel pays to, with no audit trail
- Category: auth / money-correctness
- Location: `server/routes/admin/contractorTipPage.js:43-103` (PATCH, `requireAdminOrManager`, no `logAdminAction`), `server/routes/admin/payroll.js:29-45` (`loadPeriodWithPayouts` projects `pp.preferred_payment_method, pp.venmo_handle, pp.cashapp_handle, pp.paypal_url, pp.zelle_handle`), `client/src/pages/admin/payroll/PayPanel.js:24-59,106-116` (`methodHandle` / `buildPayUrl` build the Venmo/Cash App/PayPal deep link from those columns; `markPaid` posts `payment_handle: handle`), `server/routes/admin/users.js:85-106` (the stated least-privilege rule: managers get `payment: {}` because "the payroll/financial tier stays admin-only")
- Reachable by: manager
- Evidence: `router.patch('/contractors/:userId/tip-page', auth, requireAdminOrManager, ...)` (contractorTipPage.js:43) accepts `venmo_handle`, `cashapp_handle`, `paypal_url`, `preferred_payment_method` (line 49) and upserts them into `payment_profiles` (lines 96-100). The only manager guard is `ensureNonAdminTargetForManager` (lines 34-40), which protects admin accounts, not contractors. No `logAdminAction` call exists on this route (only rotate-token and regenerate-stripe log, lines 149 and 194). The admin Pay panel reads the same row: `case 'venmo': return payout.venmo_handle` (PayPanel.js:26) and `https://venmo.com/?txn=pay&recipients=${encodeURIComponent(handle)}&amount=${amt}` (PayPanel.js:42); the method defaults to `payout.preferred_payment_method` (PayPanel.js:71-73). `users.js:85-93` documents that managers must not see the payment row because "managers don't process payouts", yet the write side is open to them.
- Failure scenario: a manager calls `PATCH /api/admin/contractors/17/tip-page` with `{ "venmo_handle": "<their own handle>", "preferred_payment_method": "venmo" }`. On the next processed period the admin opens contractor 17's pay panel, which is pre-set to Venmo and generates a QR for `<their own handle>` at the locked `total_cents` (say 48,500 cents); the admin scans and pays, then `mark-paid` records `payment_handle` = the manager's handle. 48,500 cents leave the business to the wrong person; the contractor is recorded paid. Nothing in `staff_audit_log` or `admin_audit_log` names the manager.
- Existing tests: `server/routes/admin/contractorTipPage*.test.js` (if present) cover handle normalization; `server/routes/admin/payroll*.test.js` cover mark-paid drift. None asserts that a manager cannot change a payout destination; nothing enshrines it.
- Proposed fix: gate the four payout-destination fields (`venmo_handle`, `cashapp_handle`, `paypal_url`, `preferred_payment_method`) on `adminOnly` (either split the PATCH into an admin-only handle write and a manager-allowed preferred_name write, or reject those keys when `req.user.role !== 'admin'`), and add `logAdminAction({ action: 'tip_handles_change', metadata: { fields_changed } })` with no handle values in metadata. Cross-cutting consumers to keep in step: `client/src/pages/admin/userDetail/tabs/TipPageTab.js` (hide the handle form for managers), `server/routes/admin/users.js:85-106` (the stated rule), and the sibling self-service writers (`me.js` PATCH `/tip-page`, `staffPortal/paymentMethods.js`) which are correct for the owner and need no change.
- Verification: a route test mounting `contractorTipPage` with a manager JWT: PATCH with `venmo_handle` → 403 and the row unchanged; with `preferred_name` only → 200; an admin PATCH with a handle → 200 and one `admin_audit_log` row whose metadata lists `fields_changed` and carries no handle string.

### POUT-02 high CONFIRMED — Unassigning or denying a no-show after the event re-accrues only when a bonus lock moved, so their wage and tip share stay payable
- Category: money-correctness / logic
- Location: `server/routes/shifts.handlers.js:216-236,253-255` (unassign mode), `server/routes/shifts.approval.js:525-537` (PUT request → `denied`), contrast `server/routes/shifts.js:702-715` (Remove: unconditional re-accrual, added after prod 2026-08-24), `server/utils/payrollAccrual.js:533-577` (the orphan sweep that only runs inside a re-accrual)
- Reachable by: admin, manager with `can_staff` (both routes are `auth, requireStaffing`: `server/routes/shifts.js:781` and `:804`)
- Evidence: unassign: `UPDATE shift_requests SET status = 'denied' WHERE shift_id = $1 AND user_id = $2 AND status = 'approved'` (shifts.handlers.js:218), then `bonusReleased = await releaseOutOfAreaLock(dbClient, shiftId, unassignUserId)` (235) and `if (bonusReleased) reaccrueDutyForProposal(proposalIdForDuty)` (255). Deny: `UPDATE shift_requests SET status = 'denied' ...` (shifts.approval.js:526-528), then `if (await releaseOutOfAreaLock(pool, srShiftId, srUserId)) { reaccrueDutyForProposal(srProposalId); }` (535-537). Neither route has a completed-event guard. The Remove path's own comment states the consequence that was fixed there and nowhere else: "a no-show Removed after completion kept a quarter of the card tip because her shift carried no bonus, so this branch never fired" (shifts.js:710-712). The accrual's roster sweep (`orphans` filtered by `!currentKeys.has(...)`, payrollAccrual.js:566-570) is the only thing that removes an off-roster line, and it runs only inside `accruePayoutsForProposal`.
- Failure scenario: event completes and accrues: two bartenders, 5.5 contracted hours at 2,000 cents/h (11,000 wage each), 20,000 cents gratuity pool (10,000 each). Bartender B was a no-show. The admin opens the shift and uses the roster's unassign action (`POST /api/shifts/:id/cancel-or-unassign` with `mode: 'unassign'`) or sets B's request to denied. No out-of-area bonus is attached, so `bonusReleased` is false and no re-accrual fires. B's line (11,000 wage + 10,000 gratuity = 21,000 cents) stays `pending` and is paid at the next process; A is underpaid by the 10,000 cents gratuity re-split that never happened. Outcome: 21,000 cents to a person who did not work, and A short 10,000.
- Existing tests: `server/routes/shifts.removeReaccrue.test.js` pins only the Remove path ("Remove on a completed event re-accrues even with NO out-of-area lock"); `server/routes/shifts.cancelUnassign.test.js` asserts denial and message suppression only; `shifts.bonus.test.js:588` ("admin denying an approved staffer releases the lock") asserts the lock, not payroll. Nothing enshrines the defect; it is uncovered.
- Proposed fix: call `reaccrueDutyForProposal(proposalId)` unconditionally after commit in both the unassign branch (shifts.handlers.js:255) and the deny branch (shifts.approval.js:531-537), exactly as shifts.js:715 does; `maybeReaccrueForDuty` already no-ops for anything but a recently-completed proposal, so pre-event calls cost one SELECT. Rename the helper or widen its comment so it is not read as duty-only. Cross-cutting: the cancel mode of the same handler (shifts.handlers.js:190-215) should do the same, and `coverApprovalCascade.js:217` (`if (result.outOfAreaLockMoved)`) has the same gating and should be checked for the post-completion cover case.
- Verification: a sibling of `shifts.removeReaccrue.test.js` for each path: complete + accrue a two-bartender event, unassign B (mode unassign) with no bonus attached, await the re-accrual, assert B's `payout_events` row is gone, B's emptied payout is deleted, and A's `gratuity_share_cents` is the full pool; repeat for `PUT /shifts/requests/:id { status: 'denied' }`.

### POUT-03 high CONFIRMED — Accrual's prior-line lookup is keyed by contractor+shift without the pay period, so a line in another period seeds the open-period line (double wage after an event-date move; zeroed wage and doubled claw when a clawback landed in a later open period)
- Category: money-correctness / data-integrity
- Location: `server/utils/payrollAccrual.js:412-422` (the `existing` map), `:427-448` (`prior` seeds `contracted_hours`, `hours`, `rate_cents`, `late`, `adjustment_cents`), `:462-496` (the upsert into THIS period's payout), `:566-570` (sweep scoped to `payPeriodId`), `server/utils/payrollClawback.js:120-137,176-218` (claw lands in "the open period containing today", keyed by the original shift), `server/routes/proposals/crud.js:454-475,566` (admin PATCH edits `event_date` with no completed-status guard; `syncShiftsFromProposal` at 692 moves the shift), `server/utils/dutyLines.js:294-297` (the duty code acknowledges "lines can live in another (frozen) period when an event date moved weeks")
- Reachable by: admin (the event-date edit) plus any re-accrual trigger (approval/remove/bonus hooks, refund, late tip, balance webhook, process fee-recapture); webhook (the clawback)
- Evidence: `existingRes` selects every `payout_events` row for the proposal's shifts across all periods (`JOIN shifts s ON s.id = pe.shift_id WHERE s.proposal_id = $1`, lines 412-419) and builds `new Map(rows.map(r => [`${r.contractor_id}:${r.shift_id}`, r]))` (420-422): duplicate keys keep whichever row the unordered SELECT returned last. For each current worker, `prior = existing.get(key)` (428) and the line is written to `ensurePayout(client, payPeriodId, w.user_id)` for the CURRENT period (462) with `contractedHrs = prior ? Number(prior.contracted_hours) : ...`, `hours = prior && !priorHeld ? Number(prior.hours) : contractedHrs`, `rateCents = prior ? Number(prior.rate_cents) : ...`, `adjustment = prior ? Number(prior.adjustment_cents) : 0` (439-448). The sweep never touches another period's rows (567). The clawback writes a synthetic row with `contracted_hours, hours, rate_cents, wage_cents = 0, 0, 0, 0` and a negative `adjustment_cents` into whatever period contains today (clawback.js:124-137, 196-218), without checking whether the event's own period is still open.
- Failure scenario A (double wage): event Sat Oct 10 (period P1, Oct 6-12) completes and accrues (5.5 h x 2,000 = 11,000 cents + 10,000 gratuity); P1 is processed and paid on Oct 14. On Oct 20 the admin corrects a typo in `event_date` to Oct 17 (P2, Oct 13-19, open); the PATCH has no completed guard and syncs the shift date. Any re-accrual within 21 days (a Remove, a bonus edit, a refund via `maybeReaccrueForDuty`, a late tip, a balance payment webhook) resolves P2 as the period, takes the PAID P1 row as `prior`, and inserts a second payable line in P2 with the same 11,000 wage + gratuity. The contractor is paid 21,000 cents twice for one shift; P1's row is untouched by design.
- Failure scenario B (zeroed wage, doubled claw): event Sat Oct 10 in P1, not yet processed. On Tue Oct 13 (today is in P2) a 4,000-cent card tip from that event is refunded in the Stripe dashboard; `charge.refunded` → `clawbackTip` → `findOpenPeriodForDate(today)` = P2 → a synthetic (P2 payout, shift S) row with `adjustment_cents = -1936` and hours/rate 0. Before P1 is processed, a re-accrual fires (the Process button itself runs `recaptureNullTipFeesForPeriod`, which re-accrues every P1 proposal whose tip fee was null, admin/payroll.js:305-325). `existing` now holds two rows under the same key; when the P2 row wins, the P1 wage line is rewritten with `contracted_hours 0, hours 0, rate_cents 0, wage_cents 0, adjustment_cents -1936`: the worker's 11,000-cent wage is gone from P1 and the 1,936-cent claw is now booked in both P1 and P2. Which row wins is nondeterministic (unordered SELECT, Map last-wins).
- Existing tests: `server/utils/payrollAccrual.test.js:239` ("removes an off-roster worker line, keeps A, leaves a frozen-period row untouched") seeds a PAID prior-period line for B on the SAME shift and then asserts `B has an open-period line before removal` (line 287): it enshrines the double accrual of scenario A as setup state without judging it. `payrollClawback.test.js:240` (H1) uses a PAID prior period, so scenario B is uncovered.
- Proposed fix: key `existing` by `${contractor_id}:${shift_id}:${pay_period_id}` and take `prior` only from `payPeriodId` (the period being written); treat a payable line for the same (contractor, shift) in another period as a hard stop (skip that worker, Sentry warning "already accrued in period N; move the line by hand") rather than a seed. In `clawbackTip`, when the tip's shift belongs to a proposal whose own period is still `open`, land the claw in THAT period's payout (merging into the wage line) instead of today's period. Cross-cutting: `rollForwardLateTip` has the same "today's period" choice but is only called when the origin period is frozen, so it is safe as long as `matchTipToEvent` and `tips/:id/assign` keep their frozen check; `payrollAccrual.test.js:239` must be rewritten to assert the new refusal.
- Verification: (1) accrual test: paid line for (B, S) in a frozen period, event moved to an open period, re-accrue → no new line for (B, S), a Sentry capture naming the frozen period; (2) accrual test: open P1 line (5.5 h) plus a P2 synthetic claw row for the same (A, S), re-accrue P1 → P1 line keeps 5.5 h / 11,000 wage and P2 row untouched, deterministic regardless of row order; (3) clawback test: event period open, today in the next period → the claw merges into the event period's wage line.

### POUT-06 medium PLAUSIBLE — The dispute-withdrawal clawback treats `dispute.amount` as the cumulative refunded total, under-clawing a tip that was partly refunded before the dispute
- Category: money-correctness / idempotency
- Location: `server/routes/stripeWebhookHandlers/disputes.js:9-12`, `server/routes/stripeWebhookHandlers/chargeRefunded.js:24`, `server/utils/payrollClawback.js:38-42` (`newAmt = min(newCumulative, original)`, `delta = newAmt - oldAmt`)
- Reachable by: webhook
- Evidence: `charge.refunded` passes `charge.amount_refunded` (cumulative by Stripe's definition) while `charge.dispute.funds_withdrawn` passes `dispute.amount` (the disputed amount, not a running total) into the same marker: `clawbackTip(tipId, newCumulativeRefundedCents)` computes `delta = newAmt - oldAmt` against `tips.refunded_amount_cents` (clawback.js:38-42).
- Failure scenario: a 10,000-cent tip is partially refunded 3,000 (marker 3,000, 3,000 clawed net of fee). Only 4,000 is clawed; the business is out 7,000 and the bartenders keep 3,000 that was reversed. The unverified step: whether Stripe reports the dispute amount as the remaining 7,000 (its documentation says the disputed amount can be less than the charge) rather than a figure that happens to equal the cumulative.
- Existing tests: `payrollClawback.test.js:276` ("partial then full refund aggregates the delta correctly") and `payrollDisputeRewind.test.js:153` cover refund-then-refund and withdraw-then-reinstate, not refund-then-dispute. Not enshrined.

Cross-cutting: `retryDeferredTips` replays `defer_target_cents`, which must then be stored as the summed target.
- Verification: a clawback test: refund 3,000 then withdraw 7,000 → total clawed net equals 10,000 minus the whole fee, and a replay of the same withdrawal is a no-op.
