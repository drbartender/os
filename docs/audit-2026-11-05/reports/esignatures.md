# E-signatures audit: staff contractor agreement, client proposal signature, extension acceptance, W-9 (repo at 13f2645, 2026-11-05)

Summary
- Counts: 0 critical, 0 high, 8 medium, 6 low (14 findings, all CONFIRMED by code path; none needed the database to establish reachability).
- Worst thing: a signed proposal's terms are freely rewritten by the admin PATCH (package, guests, hours, add-ons, snapshot, total) with the signature left attached and no re-acceptance; the only record of what was signed is `acknowledged_total` inside one activity-log JSON row, and the client then pays the new total through a pay-only form that acknowledges nothing (ESIG-02 with ESIG-03 and ESIG-05 compounding it).
- The proposal sign route itself is the strongest piece in the domain: UUID token guard, allowlisted document version, a TOCTOU-collapsing UPDATE that asserts "unsigned, signable status, row total to the cent", proxy-validated IP, replay answered with 409 and an activity row, and seven suites pinning it.
- The staff agreement is weaker than its sibling: the signer controls the recorded IP (first X-Forwarded-For hop), the signature payload is unvalidated, the version is stamped server-side without binding what the signer rendered, a re-sign overwrites the prior record (including the SMS-consent record), and neither the signer nor the admin can retrieve the archived PDF from the app although both the page copy and the email promise it.
- Compliance posture (ESIGN/UETA basics): attribution, timestamp, document version and a signed artifact exist for both families; what is missing is a durable, retrievable copy of the record as signed (both families), an affirmative electronic-signature consent on the staff draw path, a frozen signed configuration on the proposal, and any server-side certification record for the electronic W-9.

### ESIG-01 medium CONFIRMED — The staff agreement records the signer-supplied first X-Forwarded-For hop as `signature_ip`, so the IP on the row and on the archived PDF is forgeable (same defect on the portal change-request consent record)
- Category: data-integrity
- Location: server/routes/agreement.js:92; server/routes/clientPortal/changeRequests.js:129; server/index.js:187 (`app.set('trust proxy', 1)`); server/utils/agreementPdf.js:123 (prints it); contrast server/routes/proposals/publicToken.js:475-480, server/routes/proposals/publicSwitch.js:142-147, server/routes/serviceExtensions/publicAccept.js:70-73
- Reachable by: staff (applicant / onboarded), client (portal)
- Evidence: `const ip = req.headers['x-forwarded-for']?.split(',')[0]?.trim() || req.socket?.remoteAddress || null;` (agreement.js:92). Express runs behind one proxy hop with `trust proxy` set (index.js:187), so `req.ip` is the proxy-validated address while the FIRST XFF entry is whatever the caller sent; the sibling sign route says exactly this: "req.ip FIRST: express runs behind `trust proxy`, so req.ip is the proxy-validated address while the first x-forwarded-for entry is attacker-supplied. A signature IP is the strongest artifact in a payment dispute, so it must not be the forgeable one" (publicToken.js:475-478). publicAccept.js:70-73 adds that the leftmost entry "can overflow the VARCHAR(64) column into a 22001 500". The stored value goes to `signature_ip VARCHAR(45)` (schema.sql:146) and is printed on the archived PDF (agreementPdf.js:123). changeRequests.js:129 uses the identical expression for `request_ip` of the client's acknowledged-total consent row.
- Failure scenario: a contractor signs with header `X-Forwarded-For: 203.0.113.9` from their own machine; the row, the PDF and every later dispute ("that was not me", non-solicit or indemnity enforcement) carry 203.0.113.9 instead of the real address. A value longer than 45 characters makes the sign 500 (pg 22001 is not an AppError, index.js:486), which only hurts the sender but is a second sign of the wrong header.
- Existing tests: none for routes/agreement.js at all (grep for `routes/agreement` in *.test.js is empty). publicToken.test.js Case D asserts the proposal path records an IP but not which one.
- Proposed fix: `const ip = (req.ip || '').replace(/^::ffff:/, '').slice(0, 45) || null;` in both sites (the publicAccept.js pattern); no other consumer changes (the column and the PDF already take a string).
- Verification: a supertest-style unit around the agreement router with `app.set('trust proxy', 1)`, posting with `X-Forwarded-For: 1.2.3.4, 10.0.0.1`, asserting the stored `signature_ip` is the proxy-validated address and that a 300-character header yields a 200 with a 45-char-or-less value, never a 500.

### ESIG-02 medium CONFIRMED — A signed proposal's terms (package, guests, hours, add-ons, snapshot, total) are rewritten by the admin PATCH with the signature left attached, no signed snapshot is kept, and the client then pays the new total without re-acknowledging

- Failure scenario: client signs a proposal at total_price 150000 cents (`acknowledged_total` 1500 recorded); before paying, an admin edits guest count or adds an add-on and the row becomes 185000 cents with a new snapshot and new add-on rows; the client returns, sees a pay-only card for 185000 and pays; the row now shows a signature dated day 1 attached to a configuration that did not exist on day 1, the signed add-on set is gone (deleted and re-inserted), and the business can produce only "acknowledged_total: 1500" from the log if the client disputes the 35000-cent difference. Consumers to update together (cross-cutting rule): publicToken.js sign UPDATE, crud.js PATCH, schema.sql (two idempotent `ADD COLUMN IF NOT EXISTS`), admin ProposalDetail.js signature card (show the signed total beside the version), SignAndPaySection payOnly (print the signed total), clientPortal.js projection (add the signed total, never the IP/UA), publicLeak.test.js forbidden keys (the signed snapshot must be sanitized the same way as `pricing_snapshot` if exposed).
- Verification: a crud PATCH suite case: insert a signed, unpaid 'accepted' proposal, PATCH guest_count, assert either 409 `SIGNED_UNPAID` or that `client_signed_at` is NULL and status is 'sent' and a `signature_voided` row exists; a publicToken.signTotal case asserting `client_signed_total` equals the asserted total and `client_signed_snapshot` equals the rendered rows.
