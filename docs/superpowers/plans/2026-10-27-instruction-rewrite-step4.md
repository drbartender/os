# Instruction rewrite, step 4: docs from code, live from its merge

**Goal:** make README and ARCHITECTURE true by construction where they mirror code, and make a stale doc or a header-less source file refuse the commit instead of warning. Six sections are generated from the tree, package.json, .env.example, the route mounts, schema.sql and the agent files; every source file carries a header comment the tree reads; the 548 files without one get it by a one-time migration whose receipt is the comment-only proof of spec 3.7; every row of the two env tables lives in .env.example, the one copy; the merge path regenerates after every squash; the pre-commit hook runs the check. Unlike step 3, nothing here is dormant: from the merge of the last lane every commit in every window meets the check, and the four lanes cut before the flip rebase over the header migration before their review.

**Spec:** `docs/superpowers/specs/2026-10-19-instruction-rewrite-design.md` (rev 6), sections 3.7 (the comment-only kind), 4.1 (the merge path's regeneration), 4.2 (the quick fix runs npm run docs first), 4.7, 5 in full, 7 (the rows for gen-docs.js, migrate-headers.js, check-docs-drift.sh, .husky/pre-commit, .env.example, README.md, ARCHITECTURE.md, package.json, merge-lane.sh), 8 item 4, 9 (the markers and output format, the header block format, the comment-only proof, the route-row match rule), D5, D11, D12, D13. The step 2 plan's receipt contract (the kinds, the keys, `--proof`, the exemptions of comment-only) and the step 3 plan's amendments bind as built.

**Decisions this plan makes on what the spec left to the builder (section 9) or left open, stated here so Dallas sees them and can reverse any. Three of them (4, 15, 20) add to or change settled text rather than resolve an open point, and say so:**

1. **A source file, for the header rule and the gate, is a tracked non-test `.js`, `.jsx`, `.mjs` or `.cjs` file under `server/`, `client/src/` or `scripts/`** (the content rule's roots; tests excluded as the ratchet excludes them). A `.sh`, `.sql` or `.css` file gets a tree description when it has a leading comment and is never required to. The header is the first comment after the optional shebang, `'use strict'` and eslint-directive lines, and its description is the comment's first paragraph (up to the first blank comment line), one line in the tree however long. My call: the spec's "first comment" with the paragraph rule so a long header reads as one line.
2. **A file the README never described gets a header generated from its exports that says it was generated** (a React component's name and kind, the named exports, or "entry point"), so the next hand that opens the file replaces it; a blank or a lie would be worse than an honest placeholder. 114 of the 548 header-less files have a README description; the other 434 (nearly all under client/src) get the generated form.
3. **The generated tree omits test files and describes no directory.** Today's tree described 42 directories; the migration prints those descriptions to the step ledger and the restructure lane folds into README's hand prose only one that states something no file header does (the docs/ line, the audio assets line). Within a directory, files come first then subdirectories, each in byte order. The top level is listed one line per tracked file or directory, with the three roots descended in full and every other directory shown as a name and a file count.
4. **Six generated sections, each between `<!-- gen:<name> -->` and `<!-- /gen:<name> -->` markers**: `tree`, `scripts` and `env` in README; `routes`, `schema` and `agents` in ARCHITECTURE. The generator never creates a marker: a missing or doubled marker fails `--check` and `npm run docs` naming the file and the section. The `agents` section is an addition the spec does not name (5.1 lists five): the names, models and descriptions of every `.claude/agents/*.md` front matter plus the commands and skills, replacing ARCHITECTURE's hand "Claude Code Review Agents" section, which still names the fleet cut in step 2. My call: it is a mirror of files, exactly D5's case, and it is small; drop it and the hand section is rewritten by hand instead.
5. **The scripts table carries Script and Command only**, from package.json; a hand "script notes" list below the markers keeps the caveats today's table carries for the scripts whose command does not say what matters (`test`, `test:smoke`, `gate`, `worktree:new`, `worktree:rm`, `lane:status`, `check:css-scope`), cut to the caveat. package.json has no description field and inventing one would be a second mirror.
6. **The env table carries Variable, Default and Description; the Required column is dropped as a column and ported as words.** The description is the comment block directly above the variable in .env.example; the default is the value in the file, or "unset" for a commented-out line. A README row's Required cell other than "No" or "Optional" (on 2026-10-27: 4 "Yes", 2 "Yes*", 1 "Bootstrap", 41 "For <something>") opens the block as a phrase ("Required." "Required for payments."), and "Optional" is kept where the block does not already say it, so no row loses its cell. .env.example is brought to one convention by the port lane: a section heading is a comment line followed by a blank line; a variable's block sits directly above it with no blank line between; a block above several adjacent variables describes each. The CLAUDE.md env table goes in this step too, replaced by one pointer line to .env.example, a departure from section 7, which places every CLAUDE.md change in step 5: the port is checked here, and a copy left behind drifts from the day it is left. The invariants manifest still matches without the table (checked 2026-10-27).
7. **The route table is a static parse through acorn and never a require.** `server/index.js` is parsed for `app.use('<prefix>', <router>)` mounts and its own `app.<method>` routes; each router module is parsed for its Router instance, its `<method>('<path>', ...)` calls, its `.use()` calls (a nested mount when the argument resolves to a module that creates and exports a Router, by inline `require`, by a `const` bound to one, or by destructuring; router-level middleware otherwise, applied to every route registered after it in that file) and the comment directly above each route call. One table per mount statement, in mount order, rows in registration order (order is behavior for express), columns method, full path, auth (the middleware names present, or `public`), handler file and line, and the comment above the handler. Anything the walker cannot resolve (a path that is not a string literal, a router expression it cannot follow, a `.route()` chain) is an `unparsed` row naming the file and line, and fails `--check`. The runtime walker `scripts/route-inventory.js` stays as the oracle the gen-docs lane checks itself against, mount by mount.
8. **A route row moves into a handler comment only when it matches exactly one handler by method, mount prefix and path, the handler has no comment above it, the row's description is at most 400 characters, and the file stays at or under 1,000 lines after the insert.** The last two conditions are mine, beyond 5.1's one criterion of unambiguity: a 4,000-character comment above a handler is the mega-file growth the ratchet exists to stop, and no route file may cross the cap by a comment. Every other row, and the 93 prose lines between today's tables, goes to a hand "Route notes" section after the generated table, keyed by mount and path. The static estimate on 2026-10-27 is 348 of 388 rows matching one handler and 0 matching more than one; 97 rows are over 400 characters and stay in the notes. No second fuzzy pass (5.1).
9. **The schema index lists, per CREATE TABLE in `server/db/schema.sql`, the table with its line, its description (the `--` comment block directly above it, when one is there), its columns from the CREATE body and from every ADD COLUMN statement for it anywhere in the file, its constraints (from the body and every ADD CONSTRAINT, inside DO blocks included), its indexes and its triggers, each with a line pointer.** The 87 table paragraphs ARCHITECTURE carries today move as they are into a hand "Schema notes" section after the generated index, keyed by table; nothing is written into schema.sql (it is sensitive, re-executed on every boot, and 1,100 lines of prose do not belong in it).
10. **The within-section trim of kept prose ("each is cut to what the code does not say", 5.2) is deferred to a docs pass after the flip**, carried in this step's report under deferred items (for Dallas's list) and named in step 5's plan as a post-flip item. This step makes the cuts the spec names outright (README's Key Features and its three hand mirrors; ARCHITECTURE's "Plan-execution review cadence", its hand route tables and its agents section), the moves (route notes, schema notes) and the corrections it names (the database is Neon, not Render-managed; the Render settings are in docs/dev.md; README's local-dev section points at docs/dev.md). A judgment trim of 1,500 lines of money and auth prose lands at tier docs with no lens, so nothing downstream would catch a deleted rule; the generated sections are the drift fix, and the trim can wait.
11. **The comment-only proof is token equality, and it lives in its own script and library** (`scripts/comment-only-proof.js`, `scripts/lib/commentOnly.js`), not inside `migrate-headers.js` as section 7's row says: the migration is one-shot and the proof is permanent (the receipt tool reads it for every comment-only change from now on). For a `.js`, `.jsx`, `.mjs` or `.cjs` file, both versions are tokenized with acorn (acorn-jsx for `.jsx`), comments dropped, and the two token sequences must be identical in type and value; a tokenizer error on either side fails the file. For `.sh`, `.sql` and `.env.example` the rule is by line: every added or removed line is blank or a comment line (`#`, `--`, `#`) and the non-comment lines are identical in order. A file of any other kind in the diff, and any file added, deleted, renamed, copied or mode-changed, fails the proof. The proof writes JSON naming the base and tip it proved (or the staged tree) and every file's verdict; finalize accepts `--kind comment-only` only when the proof says ok, its base and tip (or tree) are the review's, and every file of the review's diff is in it. Known limit, stated: in .env.example a commented-out `# VAR=value` line is a comment, so changing the sample value on such a line passes as comment-only; the template is never read by code.
12. **acorn and acorn-jsx become devDependencies pinned at the versions already installed** (8.16.0 and 5.3.2, today transitive through eslint), through an edit of package.json and `npm install --package-lock-only` from os, never `npm install` in a lane (memory: it clobbers the shared node_modules link). The pin lives in comment-proof; gen-docs requires acorn too and runs on the transitive copy until comment-proof merges. The proof's correctness rests on the tokenizer being there.
13. **The generator reads through git.** Default: the index for the file list and the working tree for content (so a `git add`ed new file counts and an untracked scratch file does not; one stderr line names untracked source files under the roots). `--staged`: the index for both, and after writing it adds README.md and ARCHITECTURE.md, refusing first when either has an unstaged change, so a hand edit is neither swept in nor clobbered. `--ref <sha>`: that commit alone. `--check` takes the same three sources, writes nothing, and reports every problem class in one run (a marker problem, a stale section, an unparsed route, a header-less file). It uses git commands, never `.git/index`, so a pathspec commit's temporary index and a lane's own index read right.
14. **The pre-commit check is `--staged`**: the six sections against the whole index, the header rule against the staged added and modified source files; exit 1 names each problem and ends with the one line to run. The whole-tree check at ship is step 5's wiring (5.1); `--ref` exists here for it.

The generated paths are outside every receipt key (3.7), so the regeneration changes nothing a receipt vouches for. merge-lane.sh is on the matcher's hinge set today (the D11 set is carried as globs since step 2), so the lane is hinge.

The claudemd-invariants key `doc-updates` already matches "header comment".

## Contracts shared across lanes

These are the decisions the lanes build to; a lane that finds one wrong rules and ledgers it, and the plan's Amendments carry the ruling, as the step 3 plan did.

**The header rule (`scripts/lib/genDocs/headers.js`).** `isSource(path)` is decision 1's set, from a tracked path; `readHeader(text, ext)` returns `{present, description, start, end}`: it skips leading blank lines, a shebang line, a `'use strict'` directive (single or double quotes, with or without the semicolon), and eslint directive comments (`/* eslint... */`, `// eslint...`), then takes the first comment: a run of consecutive `//` lines with no blank line between, or one `/* ... */` block. The description is the first paragraph: the comment's lines with `//`, `/*`, `*`, `*/` and one leading space stripped, up to the first blank comment line or the comment's end, joined with single spaces and trimmed; an empty description is no header. For `.sh` the comment lines are `#` after the shebang (a `# shellcheck` line skipped), for `.sql` `--`, for `.css` one `/* */` block. `insertionPoint(text, ext)` is the line index after the skipped prefix, where a header goes; a byte-order mark is kept first and CRLF endings are preserved by the writer.

**The sources (`scripts/lib/genDocs/source.js`).** `open({mode, ref, cwd})` with mode `worktree` (default), `staged` or `ref`; `list()` returns the tracked paths (`git ls-files -s` for the index, `git ls-tree -r` for a ref; the index list in worktree mode too); `read(path)` returns the content from the working tree, the index (`git cat-file --batch` over the index's blob ids) or the ref; `untrackedSource()` in worktree mode returns untracked, non-ignored source files under the roots for the stderr line. Every git call honors `GIT_INDEX_FILE` by using git itself. Content reads are batched so a full generation stays under three seconds on the real repo.

**The markers (`scripts/lib/genDocs/markers.js`).** `replaceSection(text, name, body)` replaces everything between `<!-- gen:<name> -->` and `<!-- /gen:<name> -->` (the marker lines kept, the body between them, the first body line `Generated by npm run docs; do not edit between the markers.`) and reports, naming the file and section, when the marker is absent or appears twice (`npm run docs` stops on it; `--check` lists it and goes on); `readSection(text, name)` returns the body or null. The markers and their names are fixed: `tree`, `scripts`, `env` (README.md), `routes`, `schema`, `agents` (ARCHITECTURE.md).

**The tree (`scripts/lib/genDocs/tree.js`).** `render(source)` returns the fenced tree of decision 3: the top-level entries in byte order, files first, each file with its description when `readHeader` finds one; the three roots descended with the same rule at every level, test files omitted (one line under the fence header: `tests omitted: <n>`), every other top-level directory as `<name>/ (<n> files)`; a line is `<branches><name>` padded to 30 characters then `# <description>`, or the name alone when there is no description; the box-drawing characters are today's (`├── `, `│   `, `└── `).

**The scripts table (`scripts/lib/genDocs/scriptsTable.js`).** `render(packageJsonText)`: `| Script | Command |`, one row per key of `scripts` in file order, pipes escaped.

**The env table (`scripts/lib/genDocs/env.js`).** `parse(text)` reads .env.example by decision 6's convention into sections, each a heading and its variables, each variable `{name, default, active, description}`; `render(parsed)`: one heading line per section and a `| Variable | Default | Description |` table under it, the description the block's lines joined with single spaces, pipes escaped, `unset` for a commented-out variable, the literal value otherwise (the file holds no secret; it is a template). A variable line with no block above it renders an empty description, never fails.

**The route table (`scripts/lib/genDocs/routes.js`).** `walk(source)` returns `{mounts: [{prefix, file, line, routes: [{method, path, auth: [names] | 'public', file, line, description, unparsed: null | reason}]}], problems: []}` by decision 7: index.js parsed with acorn (`ecmaVersion: 'latest'`, `sourceType: 'script'` then `'module'` on failure, `allowHashBang`, `onComment` collected with positions) for `app.use(<string>, <expr>)` statements in order and `app.<method>(<string>, ...)` routes; a router expression resolved as an inline `require('<rel>')`, `require('<rel>').<prop>`, or an identifier bound at the top level of the same file by `const x = require(...)`, `const x = require(...).<prop>`, `const { x } = require(...)` or `const { router: x } = require(...)`; a module resolved by its path (`.js`, then `/index.js`); inside a module the Router is any top-level `const <name> = express.Router(...)` or `Router(...)` from a destructured `require('express')`, and its export is `module.exports = <name>`, `module.exports = { <name>, ... }`, `module.exports = { router: <name> }` or `module.exports.<prop> = <name>`; `<name>.<get|post|put|patch|delete|all>(<string>, ...args)` is a route whose auth is every argument but the last, each rendered as its identifier, or `<callee>(...)` for a call, prefixed by the router-level middleware in effect; `<name>.use(...)` with a router argument is a nested mount at the given string prefix (or the parent's when none), and with no router argument is router-level middleware for the routes after it in that file; the description is the comment ending on the line directly above the route statement, first paragraph, by `readHeader`'s stripping; anything else is an `unparsed` row (`{file, line, reason}`) and a problem. `render(walk)`: a `###` heading per mount (`<prefix> (<file>)`) and a `| Method | Path | Auth | Handler | Description |` table in registration order, nested routes with their full path, an unparsed row as `| ? | <file>:<line> | unparsed | | <reason> |`.
