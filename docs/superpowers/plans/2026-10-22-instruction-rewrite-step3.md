# Instruction rewrite, step 3: the gate on the range, the ship path, the watch, dormant

**Goal:** build the push half of "main is prod" as scripts with tests, all dormant behind a flip marker that step 5 writes: a gate that tests a commit in isolation, classified by the push range; one push path that checks the review receipts over the range, gates, pushes the literal sha and starts a watch; a watch that waits for the deploy and reads Sentry against a baseline; two markers every push path refuses on; and the session-start line that prints them. Until the marker exists nothing about pushing changes: `npm run gate` and a literal-sha push stay the way, the hook falls through to today's fingerprint check, and the board writer keeps its guarded push.

**Spec:** `docs/superpowers/specs/2026-10-19-instruction-rewrite-design.md` (rev 6), sections 3.7, 3.10, 3.11, 4.1 to 4.8, 7, 8 (step 3), 9, D1 to D4, D11. The step 2 plan's "Contracts shared across lanes" (the receipt, the keys, the tier, the locks, the smoke summary) binds this step as built, through its "Amendments (rev 3, as built)".

**Decisions this plan makes on what the spec left to the builder (section 9) or left open, stated here so Dallas sees them:**

1. **The flip marker is `<git-common-dir>/drb-flip.json`**, `{sha, pushed_at, written_by}`, written by step 5's shipping session after the flip push is confirmed on origin and read by every push path from this step on. The spec names the marker without a path; the common dir is where every worktree of the repo sees one file, and this box is the only pusher.
2. **The sha gate receipt is keyed on the sha alone and records the tree hash without keying on it.** A review-time smoke runs in the lane's checkout under the box's `.env`; the gate's worth is its environment (its own env file, a private `npm ci` when a lock changed), so honoring a smoke run elsewhere would hand back exactly what the gate adds. The tree hash is recorded so a later step can change this without a receipt format change. Cost: one eight-minute smoke per tier A ship on top of the review's.
3. **The gate env file** holds `NODE_ENV=test`, `SEND_NOTIFICATIONS=false`, `RUN_SCHEDULERS=false`, a fixed throwaway `JWT_SECRET`, a fixed throwaway 64-hex `ENCRYPTION_KEY`, and `STRIPE_TEST_MODE_UNTIL=` (empty), and no Stripe key: the box's `.env` carries live keys only and no `*_TEST` credential (names checked 2026-10-22), and the money smoke suites that touch Stripe fake it through the `getStripe` seam (`stripeCreateIntent.test.js` is the precedent). `getStripe()` therefore returns null inside the gate, and a suite that fails for want of a key is a suite reaching live Stripe from the gate, a finding against the suite and never a reason to copy a live key in. This departs from spec 4.3's "the Stripe test credentials the suites read", which assumed credentials the box does not hold. `DATABASE_URL` is set per suite by `testdb-smoke.js` (ci-smoke). The smoke is spawned with a scrubbed environment (PATH, HOME, LANG, TMPDIR, `NEON_API_KEY` when set, and the file's variables; nothing else inherited), because dotenv never overrides a variable already in the process. The gate-sha lane verifies the set by running the full smoke with it once; a variable it adds is named in the lane report with the suite that needed it.
4. **No `client/.env` in the gate worktree.** The build gate compiles; a missing `REACT_APP_*` bakes an empty string, which the gate does not judge, and the Vercel build carries its own environment.
5. **The watch window is ten minutes after the deploy is observed, polling every twenty seconds; the deploy wait bound is twenty minutes for Render and fifteen for Vercel**, counted from the watch's own start line, with one health read before any bound check (never from the push or the stamps: a watch spawned by a late completion would otherwise expire unread). The Sentry read is the project events endpoint (`/api/0/projects/dr-bartender/<project>/events/`) with the token from `~/.sentryclirc`, paged newest-first until the window's start, for two windows of equal length either side of the deploy instant, grouped by issue: an issue with no events in the pre-window counts in full, an issue with events in both counts only when the post-window count exceeds the pre-window count. This departs from spec 3.11's "with `sentry-cli`": `sentry-cli events list` has no time filter, and the issues endpoint would miss events on a resolved issue, which 3.11 says must count. The health URL is the Render service's own (`https://os-g7oa.onrender.com/api/health`, from `render services`); the Vercel check is `vercel ls os --scope drbartenders-projects --format json` filtered to `target: production` and `meta.githubCommitSha` equal to the sha, state `READY`.
6. **The ship log is one line per event**, `<ISO time> <stage> <text>`, at `<git-common-dir>/drb-ship/<sha>.log`, ending in at most one `result <ok|ok-no-push|refused|failed|pushed-elsewhere> <text>` line (a push whose outcome stayed unknown has none, and its manifest carries `push_unknown_at`, until a later run completes it); beside it `<sha>.json` is the manifest the watch and lane-status read, `<sha>.watch.log` the watch's own log, and `drb-ship/last` holds the sha of the latest ship started. `lane:status` reads the manifest, never the log's prose.
7. **The SessionStart hook runs `node scripts/show-location.js && node scripts/lane-status.js --session-start`.** `--session-start` prints the markers, the flip state, the last ship, an in-flight ship and the stale lanes in at most a dozen lines and exits 0 whatever it finds, a caught crash and a failed require included (one line naming it). The plain CLI keeps its non-zero exit on a stale lane.
8. **The receipt check over a range reads every commit in `origin/main..sha`** with rules per receipt kind (the range-check contract): a docs-only commit needs no receipt; a reviewed commit's receipt is found by key, and its verdict tables and runner logs are re-read, never its summary (3.7); a clean revert is proven by its tree; a comment-only receipt is accepted on its proof. A merge commit in the range is refused (main holds squashes only). The hook and `ship` call the one function.
9. **A clean revert is recognized by tree equality (4.8)**: for a commit whose message carries `This reverts commit <sha>`, the reverted sha must be an ancestor of `origin/main` (a shipped sha), and in a temporary index (`GIT_INDEX_FILE`) `read-tree <parent>` then `apply --cached --reverse` of the reverted commit's diff must `write-tree` to exactly `<commit>^{tree}`. `ship` writes a `revert` receipt (`written_by: ship`, no lenses, the reverted sha recorded) when the proof holds, and `rangeCheck` recomputes the proof for every `revert` receipt it meets rather than trusting it. A revert whose reverted commit is itself a revert is a change that re-lands reviewed code on a moved main, not a clean revert: `ship` writes no revert receipt for it and `rangeCheck` refuses one, so it takes a lane or quick-fix receipt (2026-10-23).
10. **Lock order: ship, then push-gate, then smoke.** `ship` takes `<git-common-dir>/drb-ship.lock` blocking through `flockExec.underLock` with the guard variable `DRB_SHIP_LOCK`; a caller that already holds the lock (step 5's `merge-lane.sh ship`) sets the guard and `ship` runs inside it, which is the entry point 4.5's "calls the same code" needs, alongside the exported `shipFlow`. Sha mode keeps today's non-blocking `drb-push-gate.lock` (a second gate refuses, as today, so two gates never reset ci-smoke under each other even when one runs by hand outside `ship`); the smoke takes its own lock inside. The hook's new path takes no lock (4.3). `merge-lane.sh` keeps `merge-lane.lock` until step 5 moves it onto the ship lock.
11. **The gate worktree lives at `<worktrees dir>/.gate-<sha7>/`**, detached, beside the lanes on the same filesystem (a private `npm ci` is too large for a tmpfs), removed on exit and on every stop signal, and swept on the next gate start when a crash left one. `lane-status` never lists it: it is detached and `listLanes` keeps branches only. A docs-only range creates no worktree at all: sha mode writes the `nothing_to_run` receipt and returns.
12. **`ship` detaches by default** (spec 4.1: the foreground limit is ten minutes and a tier A gate is longer), prints `ship: started <sha7>, log <path>` and exits 0 at once; the session reads the log for the `result` line. `--foreground` keeps it attached (tests, the board writer, and step 5's merge path). `--status [<sha>]` prints the manifest and the log's last lines.
13. **`--ack-watch <sha> --note <text>`** clears the watch marker only when it names that sha, writes the note to that ship's log as an `ack` line, and pushes nothing; the note is the "what it saw and decided" of 4.4 and the ship report quotes it.
14. **The hook's new path covers pushes to `refs/heads/main` only**; a push to any other remote ref is refused with a line naming it and `--no-verify` (lanes never push branches; a lane tip has no per-commit receipts and no sha receipt, so it could never pass the range rules).
15. **`worktree:new` takes over the lane memory-root link** from the `drb` wrapper (6.5; the wrapper's own comment says step 3 does this) and `worktree:rm` removes it; the wrapper keeps its link code as a fallback for a worktree made before this step.
16. **Fix forward through `ship`:** a standing gate marker refuses unless the sha being shipped is a descendant of the marker's sha, in which case the gate runs and a pass clears the marker (4.4's fix-forward, through the one push path rather than a by-hand gate); a standing watch marker always refuses until acked.
17. **The sensitive list's gate block gains `scripts/lib/markers.js`, `scripts/lib/gatePaths.js`, `scripts/lib/rangeCheck.js` and `scripts/ship.js`**, each in the lane that creates it (the step 2 precedent for the runner files): they decide whether a push happens, so they get the smoke, verify and the externals now rather than at the flip. The watch, lane-status, the board writer and the worktree links read them and stay hinge.
18. **The gate is always called by `ship`** (the sha receipt is never written by anyone else), and `rangeCheck` always runs first; the gate's range classification is `gatePaths.touches` plus `sensitive-match.isDocsOnly`, the one classifier the manifest's `touches_client` also comes from.

## Review focus

The five ways this step bites, each pinned to a check:

1. The legacy gate or the hook regresses before the flip, so the flip push itself (which goes through the legacy path) fails or passes ungated: every existing push-gate case stays unchanged in text and green, and `verify` with no flip marker behaves as today on every stdin shape (gate-sha, checks 1 and 2).
2. The sha gate classifies from the tip commit instead of the range, or honors a receipt from before origin/main moved, so a money change earlier in the range ships without the smoke: the classification cases cover a server change two commits back and a receipt whose recorded base is no longer origin/main (ship-state check 2; gate-sha checks 5 and 6).
3. A commit with no receipt, a receipt whose tables leave a file out, a receipt whose summary says what its tables do not, or a tier A receipt with no smoke log, passes the range check: each is a refusal case with a real receipt written through the step 2 tooling (range-check, check 1).
4. The ship lock, the gate lock and the smoke lock take each other in the wrong order, or a detached ship leaves no result line, so two ships interleave or the window waits on a log that never ends: the lock-order test and the kill-mid-ship test (ship, checks 4 and 5).
5. The session-start hook exits non-zero or hangs, breaking every session, or the board writer pushes other windows' commits before the marker: `--session-start` on a repo with a broken marker file or a failed require exits 0 in under two seconds, and the board writer without the marker is the untouched guard (session-status check 1; board-ship check 1).

## Contracts shared across lanes

These are the decisions the lanes build to; a lane that finds one wrong rules and ledgers it like the step 2 plan did.

**The common dir layout.** Everything this step writes outside the tree lives under `git rev-parse --path-format=absolute --git-common-dir`, resolved from the cwd through `receipt.commonDir`: `drb-flip.json` (read only this step), `drb-markers/gate.json`, `drb-markers/watch.json`, `drb-gate/<sha>.json`, `drb-ship/<sha>.log`, `drb-ship/<sha>.json`, `drb-ship/<sha>.watch.log`, `drb-ship/last`, `drb-ship.lock`. The existing `drb-push-gate-receipt.json` (per worktree, `--absolute-git-dir`), `drb-push-gate.lock`, `drb-smoke.lock`, `drb-devdb.lock`, `merge-lane.lock` and `drb-review/` are unchanged. Every write is atomic (temp file plus rename, the pattern `receipt.js` uses).

**`scripts/lib/markers.js`.** `flip({cwd})` returns `{sha, pushed_at, written_by}` or null; `gate({cwd})` and `watch({cwd})` return the marker or null; `setGate({sha, reason, gates, cwd})` refuses (returns `{written: false, reason}`) unless the sha is an ancestor of `refs/heads/main`; `clearGateIfDescendant(sha, {cwd})` clears when the marker's sha is an ancestor of the given sha and returns what it did; `isFixForward(sha, {cwd})` says whether the standing gate marker's sha is an ancestor of the sha; `setWatch({sha, deploy_at, count, by_issue, cwd})`; `clearWatch(sha, {cwd})` only when the marker names that sha; `standing({cwd})` returns `{gate, watch}` for the refusal lines every push path prints: `BLOCKED: gate marker stands on <sha7> (<reason>); fix forward on a descendant and ship again` and `BLOCKED: watch marker stands on <sha7> (<count> events since deploy); read them, then npm run ship -- --ack-watch <sha7> --note <what you saw and decided>`. A marker file that is not JSON is reported as standing with the reason `unreadable marker <path>`; never silently absent.

**`scripts/lib/gatePaths.js`.** The leaf: `MONEY_PATHS` (today's list from push-gate.js plus `scripts/lib/worktreeLinks.js`, `scripts/lib/gatePaths.js` and `scripts/lib/rangeCheck.js`; the addition widens the legacy `run` classification too, which only adds gating), `CLIENT_PATHS`, `INSTALL_PATHS` (`package.json`, `package-lock.json`, `client/package.json`, `client/package-lock.json`), and `touches(base, tip, {cwd})` returning `{server, client, money, install, client_install, docs_only, files}` over `git diff --name-only base tip` (`docs_only` through `sensitive-match.isDocsOnly`). `push-gate.js` re-exports `MONEY_PATHS` and `CLIENT_PATHS` from it so its tests and `neededGates` keep their names.

**`scripts/lib/shipLog.js`.** `open(sha, {cwd})` creates the log and the manifest and writes `last`; `line(sha, stage, text)` appends one `<ISO> <stage> <text>` line (stages: `start`, `fetch`, `range`, `receipts`, `revert`, `gate`, `push`, `watch`, `ack`, `result`); `watchLine(sha, stage, text)` does the same into `<sha>.watch.log`; `setManifest(sha, patch)` merges fields atomically; `readManifest(sha)`, `readLast()`, `tail(sha, n)`; `inFlight({cwd})` returns the record `last` names (falling back to the newest manifest by `started_at` only when `last` is absent, unreadable or names no readable manifest) when it has no `result` (no result line anywhere in its log) and no `push_unknown_at` and its ship is alive (the manifest's `pid`, the opener's, answers a signal 0; a manifest with no pid falls back to the log written to in the last two hours, which also caps a reused pid), else null; `unsettled({cwd, all})` returns every record with no result whose `push_started_at` is set, excluding the record `inFlight` returns unless `all: true` (ship, under its lock, where every such record is dead), each as `{sha, state, since, manifest}` (`state` `pushed` when `pushed_at` is set, else `unknown`; `since` from `push_unknown_at`, else `pushed_at`, else `push_started_at`), every unreadable manifest first as `{sha, unreadable: true, path}` (never passed over, ahead of every readable record whatever their `started_at`), then the readable ones oldest first; `claimWatch(sha, {cwd})` is the one way a watch spawn is authorized: under the per-sha lock it answers `claimed` (it stamped `watch_started_at`: the stamp was null; or the watch log holds no non-blank line and the stamp is a zoned time older than sixty seconds, or is set but not a zoned time, or is more than sixty seconds ahead of the clock, since the claim writes only the current Z time; or the watch died, the log holding lines but no result line and last written more than sixty minutes ago, under a stamp that is not fresh), `started` (the manifest's `watch` field is set, or the watch log holds a non-blank line and the watch is not dead by that rule) or `pending` (a zoned stamp within sixty seconds of now with no watch line, or a dead log under such a fresh stamp), never a boolean (`setManifest` refuses `watch_started_at` as it refuses `result`); `unwatched({cwd})` returns every settled `ok` record with `watch_started_at` set that `claimWatch` would answer `claimed` for, as `{sha, state: never-started | died, since, last_write, manifest}` oldest first (`last_write` the watch log's last write for a died watch, null for one that never started); `setManifest` refuses `push_started_at`, `pushed_at` and `push_unknown_at` once a result stands (`SHIP_STAMP_AFTER_RESULT`); `setResult` refuses any state but `ok` once `pushed_at` is set (`SHIP_RESULT_AFTER_PUSH`) and refuses `ok` while `watch_started_at` is null (`SHIP_OK_NEEDS_CLAIM`), so an ok record always carries a claim; `line()` refuses any stage but `ack` once a result stands (`SHIP_LINE_AFTER_RESULT`); `open(sha, {cwd, offOrigin})` records the opener's `pid`, moves a record with `push_started_at` and no result aside only with `offOrigin: true` (the caller fetched and the sha is not on origin/main) and throws `SHIP_UNSETTLED` without it, and moves a record whose result is `pushed-elsewhere` aside only with the same flag (`SHIP_PUSHED_ELSEWHERE` without it); the manifest and the two logs are written durably (the file fsynced before a rename or after an append, the directory after a rename), so a stamp that precedes `git push` is on disk before the push. The shipLog header states what the library enforces and never restates the ship flow, the watch windows or the lane-status lines: those are this plan's contracts alone. The manifest: `{sha, pid, base, started_at, docs_only, touches_server, touches_client, commits: [{sha, subject}], gate: {receipt, result}, push_started_at, pushed_at, push_unknown_at, watch_started_at, result: {state, text, at}, last_stage, last_stage_at, watch: {result, count, issues, new_issues, deploy_at, finished_at} | null}`. Every text written to either log passes through `piiShapes.mask` in the pre-step's allowlisted mode, so a path or a commit subject with a shape never lands in a file lane-status prints.

**`scripts/lib/rangeCheck.js`.** `checkRange({base, tip, cwd})` returns `{ok, docs_only, commits: [{sha, subject, docs_only, kind, receipt_key, problems: []}], pii: [{file, line, shape}], problems: []}`. Per commit, in order: a merge commit is a problem; `docs_only` by `gatePaths.touches(parent, commit)` needs nothing; otherwise the receipt is looked up under `receipt.commitKey(commit)` and, failing that, under `<commit>^{tree}` (kind `quick-fix`), and must exist and be `state: final`. Then by kind: `revert` is accepted only when the tree proof of decision 9 holds now, recomputed; `comment-only` is accepted on its `proof` field naming a file in the receipt directory (no lens, no tests); every other kind (`lane`, `quick-fix`, `commit`, `squash`) is judged from the receipt directory, never from the summary: the tier is recomputed with `sensitive-match.tierFromGit({base: parent, tip: commit})` and must not exceed the receipt's `tier` in `TIER_ORDER`; the verdict tables are re-parsed from every file the receipt's `reports` list names, in `seq` order, through `receipt.parseVerdictTable` and `receipt.mergeVerdicts`, and `receipt.coverage` over the check's own `git diff --name-only parent commit` (generated docs excluded) must leave no file without a `pass` verdict (a `finding` row whose finding is neither `fixed` nor `rejected` in `triage`, a `not reached` or an `escalate` row is a problem, a rejected finding being a deferred minor or a wrong claim that the receipt records and that never blocks a push, as finalize already reads it; `allowed_not_reached` in the receipt is honored only for a row that says `not reached`); the tests are re-read from the files the receipt's `tests` entries name under the receipt directory: for tier A a `smoke` entry whose `summary.json` has `skipped: false`, no `did_not_run` and `total_fail: 0`; for tiers A, B and hinge a `suites` entry whose `summary.json` has `total_fail: 0` and whose every suite's log parses through `tapSummary.parse` with `found: true` and `fail: 0` (an empty reach is a summary with no suites and stands); for any `client/` file a `build` entry with exit 0. The PII scan is `piiShapes.findInDiff` in the pre-step's allowlisted mode over the pinned diff of each commit against its parent (docs-only commits included, since they need no receipt and the board writer commits docs with no review, so a shape added and removed inside the range would otherwise ship in history unseen) and over the pinned diff of `base..tip`; any hit is a problem naming the commit, the file and the line, never the text; each commit's full message is scanned with the same finder, a hit a problem naming the commit and the shape, never the text (the global rule bans a client or staff number in a commit message, and nothing else on the push path reads one). A malformed lens report a receipt lists is accepted only when a later report of the same lens, stored after it, parses well-formed (the re-emission the review skill asks for); otherwise it is a problem. A verify report a receipt lists must parse well-formed, with a finding or the `No findings` record, as finalize requires. A suite log whose TAP summary has `cancelled` above 0 is a problem like one with `fail` above 0. Every finding every listed report raised must be `fixed` or `rejected` in `triage`, not only the ids a finding row's note names. `checkRange` never reads `index.json`, `written_by` or a receipt's counts. A CLI, `node scripts/lib/rangeCheck.js <base>..<tip>`, prints one line per commit and the problems, exit 1 on any.

**The sha gate receipt.** `drb-gate/<sha>.json`: `{version: 1, sha, tree, base, files, gates_needed, gates_passed, nothing_to_run, static_checks: {blocking, file} | null, node_modules: 'linked' | 'npm ci' | null, env_keys: [names], started_at, finished_at}`. Valid for a push when the sha matches, `base` equals the current `origin/main` after the fetch, every needed gate is in `gates_passed` (or `nothing_to_run`), and `finished_at` is under seven days old. A money gate that skipped for want of a key is never in `gates_passed` (guard 5 kept). A docs-only range, and a range touching only hinge or tier B files outside `server/`, `client/`, the money paths and the install paths, is `nothing_to_run` (4.3), written without a worktree.

**`push-gate.js` modes.** `run [ref]` (legacy, unchanged in behavior), `verify` (the hook's; branches on `markers.flipState`: absent, today's path including its lock, the markers unread; unreadable, refuse with `standing().flip`'s line; present, the new path with no lock: deletes and empty stdin as today, malformed refuses as today, a remote ref other than `refs/heads/main` refuses, then per pushed sha the markers, the sha receipt, `rangeCheck` against `origin/main`), `sha <sha>` (the gate in a worktree, classified from `origin/main..sha` after a fetch; writes the receipt; on failure sets the gate marker when the sha is on main, through `markers.setGate`; on a pass clears a marker the sha descends from; prints the receipt path; exits 1 on any failure, a failing `npm ci` included), `receipt <sha>` (prints the receipt or `none`). Exports: `classifyRange(base, tip)` (built on `gatePaths.touches`), `checkShaReceipt(receipt, {sha, base, needed, now})`, `gateEnvFile()` (the text of decision 3), `gateWorktreePath(sha)`, and the existing exports. A classification that touches `server/` or `client/` also runs `static-checks.js --base <base> --tip <sha>` in the worktree; a blocking finding fails the gate with the file named. The smoke runs as `node <wt>/scripts/testdb-smoke.js --tap-dir <wt>/.gate-smoke` with the scrubbed environment of decision 3 and is read from its `summary.json`; the build as `CI=true npx react-scripts build` in `<wt>/client`. Test overrides, each named in one stderr line when set: `DRB_GATE_SMOKE_CMD`, `DRB_GATE_BUILD_CMD`, `DRB_GATE_INSTALL_CMD`.

**`scripts/lib/worktreeLinks.js`.** `LINKS`: `[{rel: 'node_modules', shared: true}, {rel: 'client/node_modules', shared: true}, {rel: '.husky/_', shared: true}, {rel: '.env', shared: false}, {rel: 'client/.env', shared: false}]`; `linkInto(target, mainRoot, {env, log})` makes the shared links always and the env links only with `env: true`, with worktree-new's existing rules (skip a missing source with a warning, leave a real path in place, report an existing link); `unlinkFrom(target)` removes link entries only (worktree-rm's order). `memoryRoot(worktreePath, {home})` returns the Claude Code project memory path for a folder (`<home>/.claude/projects/<path with slashes as dashes>/memory`); `linkMemory(worktreePath, mainMemory, {home})` applies the wrapper's rule (a link is left; a real directory is archived under `<mainMemory>/_archive/lane-<name>-<file>` then replaced; anything else refuses); `unlinkMemory(worktreePath, {home})` removes the link when it is one and leaves anything else. `worktree-new.js` calls `linkInto(target, mainRoot, {env: true})` and `linkMemory`; `worktree-rm.js` calls `unlinkFrom` and `unlinkMemory`; the gate calls `linkInto(wt, mainRoot, {env: false})` and writes its own `.env`.

**`ship.js`.** `node scripts/ship.js [--no-push] [--foreground]`, `--ack-watch <sha> --note <text>`, `--status [<sha>]`. Exports `shipFlow({cwd, noPush, log})` for step 5. The flow, each stage a log line: take the ship lock (blocking, one line when it waits; skipped when `DRB_SHIP_LOCK` names the lock file, the held-lock entry); branch on `markers.flipState`: absent, refuse (`ship: no flip marker; pushes stay cue-only through npm run gate`); unreadable, refuse with `standing().flip`'s line; present, go on; the cwd must be the primary worktree on main and the sha is its `HEAD`; `git fetch origin main` (a failure never moves a record aside: with any entry in `shipLog.unsettled({all: true})`, nothing is written to any record and the run ends unknown, exit 2, before opening anything; with none and no record for HEAD, ship opens HEAD's record and writes `result failed fetch failed`, exit 1; with none and a record for HEAD standing, whatever its state, ship writes nothing and reports from that record, exit 0 when it already pushed or was pushed elsewhere, else exit 1); then the unsettled records, every entry `shipLog.unsettled({all: true})` lists, completed by evidence in order: an unreadable one refuses the run (`unreadable ship record <sha7>; fix or move it`, exit 1, nothing else written); a record whose `pushed_at` is already set is evidence the push landed: `shipLog.claimWatch` answering `claimed` spawns the watch and ends it `ok`, `started` ends it `ok` with no spawn, and `pending` leaves it unsettled with a `watch` stage line `watch claim pending for <sha7>; run npm run ship again in a minute` and ends the run unknown, exit 2 (`pushed_at` is never re-stamped); a record whose `pushed_at` is null is judged by the fetch: its sha on `origin/main`, `pushed_at` stamped through `setManifest` (`push_started_at` stays the lower bound), the watch spawned on `claimed`, `setResult` `ok`; not on `origin/main` after that successful fetch, `setResult` `failed` `push did not land`; an error thrown or a stop signal received while completing a record writes no result to it (the record stays unsettled for the next run) and ends the run unknown, exit 2; a dry run (`--no-push`, `shipFlow({noPush: true})`) completes nothing and refuses before opening while any unsettled entry stands (`an earlier push's outcome is unsettled; run npm run ship to complete it`, exit 2); then every entry `shipLog.unwatched` lists, re-watched: `claimWatch` answering `claimed` spawns the watch, anything else is left alone; nothing is written to that record's ship log (it is settled, `line()` takes only an ack there, and a line in its watch log would read as a started watch): the claim's new stamp and the watch's own start line are the re-watch's record, and ship names the re-watch on its own output; then HEAD's own record: a sha already an ancestor of `origin/main` is `result pushed-elsewhere`, decided before `shipLog.open` so a shipped sha's record is never moved aside (with no record for the sha, ship opens one and writes that result through `setResult`; with a record standing that has a result, it writes nothing and reports from the fetch alone; HEAD's own unsettled record was completed above); a record with no result and no `push_started_at` (it died before its push) is moved aside by `shipLog.open` (called with `offOrigin: true` after the fetch), then `pushed-elsewhere` when the sha is on `origin/main`, else the ship proceeds; then `shipLog.open`; `range`: every commit in `origin/main..HEAD` listed with its masked subject (the ride-along names, D4); the markers (a gate marker refuses unless `isFixForward`; a watch marker refuses); `revert` recognition and receipt (decision 9); `receipts`: `rangeCheck`, any problem is `refused`; `gate`: `push-gate.js sha <sha>`, always called, a failure is `failed`; `push`: `push_started_at` stamped through `setManifest` right before `git push origin <sha>:main` (the earliest instant the push can have landed); a rejection is `failed` with git's bracketed reason, `fetch first` or `non-fast-forward`, no fetch, no retry, the only `failed` written after the stamp in the same run; on any other non-zero exit ship fetches, retrying for about ten seconds while the fetch fails or the sha is not yet on `origin/main` (the remote can lag the client's error by one round trip): a sha found is treated as pushed (`pushed_at` stamped, the watch spawned on `claimWatch` answering `claimed`, ended `ok`); the window's end, whether the fetch still fails or a successful fetch still lacks the sha (a replica can report a landed push late, and a record settled `failed` is never completed), stamps `push_unknown_at`, writes a `push` stage line saying the outcome is unknown and to run ship again, writes NO result and exits 2, so the next run completes the record; every other ending after the stamp, an error thrown in ship's own code and a stop signal included, ends the same way, with `push_unknown_at` stamped only while `pushed_at` is null (once `pushed_at` stands the record is left for the next run to finish); before the stamp a thrown error ends `failed <message, masked>` and a stop signal `failed killed by <signal>` (every ending first reads the record this run opened, whose `pid` is this process, from disk, never from this run's memory: when a result already stands on it, that result is the run's outcome and nothing more is written, so an ending after this run's own rejection, ok or ok-no-push keeps that result and its exit; the stamp counts only on that record; an ending before this run opened HEAD's record, outside a completion, is a failure of this run with nothing written to any record, exit 1, since an earlier run's settled record must never take a stamp); then, STILL INSIDE the ship lock, `claimWatch` (the watch spawned detached, `post-ship-watch.js <sha>`, only on `claimed`), `result ok pushed <sha7>, <n> commits` written only after the child's `spawn` event has fired (an `error` event before the result takes the after-stamp ending, so a spawn that never ran leaves the record for the next run), and only then the lock released, so a ship queued on the lock never reads a live record. Overrides for tests, each named in one stderr line when set: `DRB_SHIP_GATE_CMD` (run in place of `push-gate.js sha`; must write the receipt), `DRB_SHIP_WATCH_CMD`. `npm run ship` maps to it.

**`post-ship-watch.js`.** `node scripts/post-ship-watch.js <sha> [--manifest <file>] [--health-url <u>] [--sentry-base <u>] [--vercel-cmd <c>] [--window-ms <n>] [--deploy-wait-ms <n>] [--poll-ms <n>] [--now <iso>]` and the probes `--probe health`, `--probe vercel --sha <sha>`, `--probe sentry --deploy-at <iso> [--window-ms <n>]`, which print what the watch would read and write nothing. Flow: read the manifest; `docs_only` ends with `result no deploy expected`; poll the health URL until `release` equals the sha (the deploy-wait bounds count from the watch's own `start` line, never from the push or the stamps, and at least one health read precedes any bound check, since a watch spawned by a late completion would otherwise expire unread; a `release` that is a descendant of the sha on `origin/main` ends with `result superseded by <sha7>`; the bound ends with `result deploy not observed`; the two Sentry windows hinge on the LAST instant the sha was known not yet deployed: the last health read that showed an earlier release, or the manifest's `push_started_at` when no read showed an earlier release; the after-window runs from that instant to one window past the first read showing the sha, and the pre-window is of the same length and ends at that instant, so no event after the real deploy falls in the pre-window and the after-window holds a full window after the deploy; when the span from that instant to the first read showing the sha exceeds one window (a first read already showing the sha long after the stamp, a failed first read followed by one showing it, a gap between reads wider than a window), the deploy instant cannot be placed and the watch ends with `result deploy instant unknown` and sets the watch marker with `count: null`, never quiet, since under ship's rule (b) `pushed_at` can be stamped long after the deploy); the Vercel half only when `touches_client`, the same bound, `deploy not observed` when never READY; then the Sentry read for both projects over the two windows of decision 5; `result <N> events since deploy across <M> issues, <K> new` sets the watch marker; `result no new Sentry events in ten minutes` sets nothing. The Sentry token is read from `~/.sentryclirc` (`[auth] token=`), sent as a header, never logged; a missing token or a non-200 is `result sentry unreadable (<status>)` and sets the watch marker with `count: null`, so an unreadable Sentry never reads as quiet. Log lines go through `shipLog.watchLine`, the FIRST of them a `start` line written before any read (it is the evidence `shipLog.claimWatch` reads: a claim older than a minute with no watch line is a watch that never started and may be claimed again), and one line at each later stage (each health read's outcome, the Vercel read, each Sentry page), so the log's last write stays inside `shipLog`'s sixty-minute died bound through the longest run decision 5 allows (the serial waits sum to forty-five minutes and a Sentry read can page for longer; a watch that wrote only its start and result lines would read died while running); every read (health, `vercel ls`, each Sentry page) runs under a timeout of at most two minutes, so a watch never goes silent for the sixty minutes after which the claim reads it as died; a re-watch of a dead watch appends to that watch's log and takes its bounds from its own start instant, never from the first `start` line in the file; a watch whose result line `watchLine` refuses (a second watch finished first) still sets the watch marker for what it found, since a marker only ever blocks; the manifest's `watch` field carries the result.

**`lane-status.js` additions.** `markersReport({cwd})` (the two markers, the flip state through `markers.flipState`: `flip marker: absent, pushes are cue-only through npm run gate`, `flip marker: <sha7> <date>`, or for an unreadable file the `standing().flip` line, never a read of `flip()` alone), `shipReport({cwd})` (the last manifest: `last ship: <sha7> <result> <time>`; an in-flight one: `ship in flight: <sha7> at stage <stage> since <time>, log <path>`; each entry `shipLog.unsettled()` lists (the default excludes the in-flight record), by its state: `unknown`, `ship <sha7>: push outcome unknown since <since>; run npm run ship again to complete it`; `pushed`, `ship <sha7>: pushed at <since>, unfinished; run npm run ship again to finish it`; unreadable, `unreadable ship record <sha7>; fix or move it`; each entry `shipLog.unwatched()` lists, by its state: `ship <sha7>: watch claimed at <since> never started; run npm run ship again to re-watch it`, or `ship <sha7>: watch died, last wrote at <last_write>; run npm run ship again to re-watch it`; the watch result and its marker: `shipped <sha7> at <time>, <N> events since`), both folded into `formatReport`; `--session-start` prints markers, ship, then the lanes report with the stale lines only, and exits 0, with every require of this step's modules inside the guard. The existing exports and the stale rules are unchanged.

**`board-write.sh` after the marker.** The same loop; after the commit, the writer reads the flip state through `node scripts/lib/markers.js --flip-state` (a one-word CLI the board-ship lane adds to markers.js: `absent`, `present` or `unreadable`): `absent` keeps today's guarded push; `unreadable` prints `standing().flip`'s line and leaves the board commit local; `present` means `node scripts/ship.js --foreground` replaces the guarded push: a `result ok` or `pushed-elsewhere` is success; a `failed` whose text carries git's bracketed rejection reason (`fetch first` or `non-fast-forward`; the sha in that line masks, so the match keys on the reason) triggers the loop's rebase-and-retry as today; ship's exit 2 (the push outcome unknown) prints `Board updated under '<section>' and committed; the push outcome is unknown, run npm run ship again to complete it.` and exits 0; any other refusal or failure prints `Board updated under '<section>' and committed LOCALLY, not pushed: <ship's result text>.
