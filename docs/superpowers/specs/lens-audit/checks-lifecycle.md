# Class: status-guard

Input: 147 defects (75 money, 37 open, 14 found in prod). Lenses proposed: two NEW (lifecycle-review, comms-review) plus consistency-check and security-review.

## Shape

The OS is a set of state machines (proposal, invoice, pay period, shift, drink plan, scheduled message, applicant, consult chain, opt-out) whose status columns are written in many places and read in many more, and nothing owns the machine. Each writer and reader enumerates statuses locally, so a new value (in_progress, submitted, confirmed, reopened, partially_paid, a draft invoice) is admitted by some guards and not others; the same constant name is defined more than once with different membership (BOOKED_STATUSES in server/utils/proposalStatus.js, server/routes/proposals/cancel.js and client/src/pages/admin/proposalEditor/repriceSummary.js; PAID_STATUSES in server/utils/marketingAudience.js and client/src/utils/eventDetailView.js), and the pay-period frozen predicate is inlined at least four ways. A terminal transition (archive, cancel, full refund, void, option lost) rarely fans out to its dependents, so shifts, reminders, PaymentIntents, links and locks stay live. Late or repeated writers (webhooks, sweeps, reverts, upserts, re-approves) act without re-reading the row, so they overwrite admin-set state or run conversion side effects on a cancelled event. A money write that a state predicate refuses (a credit UPDATE whose status filter matches zero rows, a payroll writer that returns on a frozen period) vanishes silently, which is the single most expensive shape in the class. Degraded flags and intermediate states are written with no clearing write and no reaper. Client-facing surfaces derive state from the wrong source (the date, the URL, a lifecycle label) instead of the row. And the send paths have no single gate: opt-outs live in five stores and most senders read one or none. The 14 checks below are grouped by those mechanisms, not by file.

## Checks

1. **Terminal-state fan-out.** When a change moves a row into a terminal or losing state (proposal archived or cancelled, full refund, invoice void, option-group loser, payment link regenerated, staffer removed from a roster), enumerate every dependent live object and close it in the same code path, or state in the diff which ones deliberately survive: shifts and shift_requests, scheduled_messages in every non-terminal status, PaymentIntents on every surviving invoice (sent and partially_paid, not only the voided ones), prior payment links, the out-of-area lock, ungrouped sibling proposals, and membership in the events feed and the auto-assign candidate query. Confirm the demoted status is one the cancel flow still accepts, so the admin is not locked out of finishing the job.
   - Trigger: a diff that writes status = 'archived', 'cancelled' or 'void'; a refund path that demotes status (refundHelpers.js, proposals/actions.js); commitGroupChoice or sweepClientAlternatives (proposalGroupCommit.js); cancelOpenInvoiceIntents and voidUnpaidProposalInvoice (invoiceVoid.js); any roster-removal route (ShiftDrawer DELETE, drop, emergency drop, cover swap, deny-after-approve); a new creator of links or intents.
   - Lens: NEW lifecycle-review.
   - Defects caught (10): D1976, D2100, D1979, D2065, D2091, D2022, D1924, D2039, D2008, D2092.
   - Row-truth docs: yes when the path is a refund (refund scope rules: allowance = headroom + contract slack); otherwise no.

2. **Late and repeated writes read the row first.** A handler that writes to a row it did not just create (a Stripe or Cal.com webhook, a payment-link or session completion, an upsert, a status revert, a re-approve, a client re-submit) must read the row's current status and admin-set flags inside its transaction and branch on them: a terminal row gets the ledger write plus a Sentry or admin alert and none of the conversion side effects (no balance invoice, hold, staff blast, shift creation, reminders, marketing, receipt, group commit or alternatives sweep); a lost first-writer-wins commit runs no side effects; an admin-set value (a consult marked completed, a reviewed preferred_name, a deactivated tip page, an approved list) is never overwritten by a lower-authority writer; a client-visible approved artifact is served from its approved snapshot, so a later edit cannot regress it or re-notify; and entry side effects fire on the from-to transition, not on the destination state, so a revert does not replay the "we received your application" email. Every provider state the handler can receive (processing, a failed intent retried with another account) maps to an OS state that the reminder ladder and the Pay CTA respect, and the handler's own idempotency guard accepts that re-entry.
   - Trigger: files under server/routes/stripeWebhookHandlers/; server/routes/calcom.js; session and link completion in server/routes/stripe.js; contractorSeed.js upserts; any PUT/PATCH that can set a status to an earlier value; shopping-list edit routes under server/routes/drinkPlans/; onboarding submit paths in server/routes/payment.js.
   - Lens: NEW lifecycle-review.
   - Defects caught (13): D2032, D2033, D2030, D2021, D2026, D2029, D1945, D2052, D1930, D1958, D1957, D2121, D1969.
   - Row-truth docs: yes on webhook paths (acknowledged_total is row truth; a ?paid=true load never renders money; webhook endpoints inherit the account API version).

3. **A refused money write must land somewhere.** Any write that moves money (the amount_paid credit, a payout_events line, a tip share, a clawback, a refund row, record-payment) and that a state predicate can refuse must do one of three things, and the diff must show which: succeed, defer with a replayable stamp (rolled_forward_at, deferred_at) that a named job replays and a test exercises, or raise (a 409 to the caller or a Sentry alert naming the row). It must never `return` on `period.status !== 'open'` and never run an UPDATE whose status filter can match zero rows without checking rowCount. A deferral that is armed must be disarmed by the event that reverses it (a dispute won clears a deferred clawback). A stub or legacy target on a shift is skipped per line, never per shift.
   - Trigger: `UPDATE proposals ... amount_paid ... WHERE ... status NOT IN (...)` (today server/routes/stripeWebhookHandlers/paymentIntentSucceeded.js lines 284-287 and 381-384 and checkoutSessionCompleted.js lines 266-269 and 278-281 exclude confirmed, which is D2028 and D2034, both open); `if (period.status !== 'open')` in server/utils/payrollAccrual.js:192, payrollClawback.js:138, payrollLateTip.js:104; writers of rolled_forward_at or deferred_at; the record-payment status guard in server/routes/proposals/actions.js; accrual gated on proposal status (balanceScheduler.js).
   - Lens: NEW lifecycle-review (money).
   - Defects caught (11): D2028, D2031, D2034, D1975, D2075, D2082, D2087, D2088, D2084, D2086, D2041.
   - Row-truth docs: yes (acknowledged_total is row truth; create-intent's total is a tip projection; payroll completion gate: sweep before every run; duty pay effective date; late-tip roll-forward into a frozen period).

4. **Pay-period freeze is one predicate.** Every reader and writer of pay_periods.status, server and client, uses one shared frozen predicate; today it is inlined at least four ways (`!== 'open'` in accrual, clawback and late-tip; `IN ('processing','reopened')` in server/routes/staffShiftActions.js:110 and :548; open-or-reopened in server/routes/admin/payroll.js:373 and :405; the client's own gate in the payroll extras screen), and each new site picks one by accident. Processing and paid are frozen; reopened is a distinct status that accrual, clawback, late-tip and fee recapture refuse and that re-enables only admin line edits, including removing a line; Process and ensurePayout re-validate the period status inside their own transaction, not from a row read earlier; Process on a reopened period must not demand attributions that accrual will then refuse to pay; and the predicate is a correlated EXISTS, never rows[0] of a multi-row result.
   - Trigger: any diff touching pay_periods.status, payout_events writers, server/utils/payroll*.js, server/utils/payrollProcessing.js (ensurePayout), server/routes/admin/payroll.js, payrollDuty.js, staffShiftActions.js, client payroll pages.
   - Lens: NEW lifecycle-review (money).
   - Defects caught (8): D1890, D1933, D1935, D1936, D1939, D2018, D2089, D2080.
   - Row-truth docs: yes (which period is now: chicagoTodayYmd, never SQL CURRENT_DATE; payroll completion gate; frozen-period line removal; contractor_profiles updated_at trigger trap).

5. **Status enumerations: allow-lists, one constant, every guard re-audited.** When a diff adds a status value, makes a transition produce one for the first time (in_progress, submitted, confirmed, reopened, partially_paid, a draft invoice), or writes a guard with `status IN (...)`, `=== '...'` or `NOT IN`, grep every guard that enumerates that column (the literal and the shared constant) and confirm the new value is admitted or refused on purpose, including the guard on the target route of every CTA that the new status unlocks. Guards are allow-lists; a denylist admits every future status. A constant defined twice with different membership is a finding (BOOKED_STATUSES: proposalStatus.js has completed, proposals/cancel.js does not; PAID_STATUSES: marketingAudience.js has deposit_paid, eventDetailView.js does not), and a status literal no writer produces ('signed') is a bug signal. A count, exists or collision check must say which statuses count (recipe-less drafts do not).
   - Trigger: a new status literal anywhere; a new or edited guard; client/src/utils/userRoutes.js and portal landing guards; a create-intent guard and the public page guard for the same row kind; sweep arm predicates (firstReplySweepScheduler.js); OPEN_STATUS_LIST in dripSiblings.js and stopDrip.js; SWEEP_STATUSES.
   - Lens: consistency-check.
   - Defects caught (11): D1918, D1968, D1944, D1967, D1892, D1905, D1973, D2071, D1996, D2059, D1952.
   - Row-truth docs: yes when the column is money-bearing (proposals money/status: dollars, and 'cancelled' is now 'archived' plus reason; off-ledger invoice labels must join OFF_LEDGER_INVOICE_LABELS).

6. **Paid-ness is derived from row money in both directions, server and client.** After any write that changes amount_paid, total_price, or an invoice's amount_due or status, recompute the proposal's payment status from the row (amount_paid against the acknowledged total) through reconcileProposalPaymentStatus in both directions, promote and demote, and fail closed on anything unparseable; auto-complete and payroll accrual hang off that status, so a demote-only ladder is a missed paycheck. A reader never maps a lifecycle label ('completed', 'confirmed') or a URL parameter (?paid=true, redirect_status) to "paid"; the settled UI state requires a signed row and a settle refetch that actually reports paid, and an unsettled refetch lands in the fallback state. An auto-void at amount_due = 0 must prove no remainder survives elsewhere, and the idempotency check for minting a replacement invoice includes status, so a voided Balance does not block its replacement.
   - Trigger: writes to proposals.amount_paid or total_price; invoices.amount_due or status; server/utils/proposalStatus.js; server/utils/invoiceLifecycle.js (createBalanceInvoice, any auto-void); client/src/pages/proposal/proposalView/paidState.js, useSettle.js, PaymentForm.js, ProposalView.js; any reader of ?paid.
   - Lens: NEW lifecycle-review (money).

7. **Every state and flag has an exit.** For each status a row can land in and each degraded flag a handler can set (email_status 'bad', phone_status 'bad', gratuity_rate_change_origin 'admin', a terminal suppression reason such as client_no_email, a local enrolled flag that mirrors a server credential), the diff names the transition out and who triggers it: a user action, a sweep, or a webhook. An intermediate row inserted before an external call (a pending refund, a connected bridge leg) has a reaper. A status that finishes only through a manual click in some shape (consult-only drink plans, a no-draw owner's payouts, plans created before derived finalize) is derived or backfilled so that shape can reach terminal, and a rule change ships with a backfill of the rows left under the old rule. The cause that clears a degraded flag (an admin fixes the address, a client confirms the number, a client adds an email) must call the clearing write; a reset route with no caller is not an exit. Count the rows sitting in the state in prod before accepting "nobody will hit it".
   - Trigger: a new status value or suppression reason; `SET x = 'bad'` or `= false` by a webhook or form; `INSERT ... 'pending'` before an external call; a "no client caller" note on a reset route; a scheduler inventory (server/utils/*Sweep.js, *Reaper.js, *Scheduler.js) with no reaper for the new state; beoFinalize.js and shoppingListApprove.js.
   - Lens: NEW lifecycle-review.

14. **Sweep and gate candidate sets are state predicates.** A sweep, reaper, prune, orphan cleanup, sibling archive, or blocking 409 gate defines its candidate set by current state read from a structural column (held_state, never a marker in a free-text note), excludes in-flight rows (dialing, processing), and computes a blocking gate over the rows eligible now, not over stale rows. An orphan sweep keeps or deletes by the line's full state (adjustment sign, held_state, confirmed), never pays wage-minus-dock to someone off the roster, and leaves a Sentry breadcrumb when it keeps a payable line. A sibling action keyed on a shared identity (client, booker_email) distinguishes admin-adjusted or live rows from auto-drafts and alerts before discarding admin work, minting a bookable sibling at catalog price, or cancelling a real single consult.
