# Admin Staff Hub

**Date:** 2026-08-19. Revised the same day: the `/review-spec` fleet's 8 blockers and 15 warnings folded in as spec text, plus the suggestions that were correctness items. Two design changes came out of it (the tips ledger's "Lands in" column and a third Reviews state), both noted in §3 as benchmark overrides.
**Status:** Approved (section-by-section 2026-08-19; IA settled in chat, visual system settled in the claude.ai/design session, the open-pay-period subtitle rule settled last; fleet fold-in delegated to Claude)
**Audience:** Dallas (admin) and the manager role. Desktop Admin OS. The phone shell is touched only where the sidebar's `nav.js` feeds it (§8); phone-first Staff surfaces remain a later mobile phase.

## 1. Problem

The Admin OS sidebar carries four entries that are all "the people who work for me": Staff, Hiring, Tips & Feedback, Reviews. Payroll is a fifth people-surface with no sidebar entry at all, reachable only from the Overview card and a staffer's Payouts tab. Tips & Feedback and Reviews sit under a "Revenue" group with Marketing, where nobody looks for them. The nav also advertises Hiring, Tips and Reviews to managers whose API calls those surfaces reject.

Checked against prod 2026-08-19 before deciding anything: one tip ever ($6.00, 2026-08-16), zero feedback rows ever, one review ever (pending, 2026-08-17), zero bounties paid. These are eight-day-old surfaces with one event day of data, not dead ones. But giving them top-level billing beside Roster and Payroll would be a hub that lies about where the work is.

## 2. Settled information architecture

One sidebar entry, **Staff**. Four children. Roster lands.

| Child | Route | Inside it |
|---|---|---|
| **Roster** (lands) | `/staffing` | Active / Deactivated / All switch over a table |
| **Hiring** | `/staffing/hiring` | Three-column kanban: Applied, Interview, Onboarding |
| **Payroll** | `/staffing/payroll` | Pay run, History, Tips, 1099 / tax |
| **Reviews** | `/staffing/reviews` | Pending cards, resolved table, contest rail (no internal tabs) |

Decisions, with the reason each was made:

- **Roster lands.** Clicking Staff shows the staff list, never a hub overview.
- **Tips fold into Payroll.** A tip is collected on one bartender's own sign, then paid as payroll: accrual pools the card tips matched to an event's shifts and splits them evenly across that event's approved bartenders (`payrollAccrual.js`, the shipped and deliberate "payroll pooling"), and late tips roll into the current open period (`payrollLateTip.js`). Either way it is payroll math, and a global cross-staff ledger standing apart from Payroll was the odd one out. Payroll's existing Tips tab (the unassigned and deferred repair queues) gains the activity ledger. One tips surface, not two a click apart.
- **Feedback leaves the hub.** `tip_page_feedback` is a rating and a comment about one bartender, submitted from that bartender's thank-you page, and `publicTip.js` already emails the operator on every submission. It is per-person, so it moves to the staffer's profile (§9). Zero rows have ever existed.
- **Reviews keeps a child.** It is the one genuinely cross-staff surface (read a review, decide who it names, credit them, run a quarterly contest across the team) and it is a real payroll input, not a log: confirming writes a `payout_duty_lines` row of `REVIEW_BOUNTY_CENTS` (`kind='review_bounty'`) and the award writes `review_contest`, both landing in the open pay run.
- **Existing detail routes stay put:** `/staffing/users/:id`, `/staffing/applications/:id`, `/staffing/legacy` (the Send SMS page) are untouched. In React Router v6 these are declared as siblings of the `/staffing` layout route (more specific static and dynamic segments rank above the layout's relative children), so they never render inside the hub chrome.

## 4. Architecture

Follows `MarketingLayout.js`: a layout component with nested routes behind one sidebar entry.

- **`client/src/pages/admin/staffHub/StaffHubLayout.js`** (new). Renders `.hub-head` (title "Staff", the live subtitle, `.hub-tabs`, the `.page-actions` slot) and an `<Outlet />`. Owns ONE fetch, `GET /api/admin/staff-hub/summary` (§5), shared through Outlet context `{ summary, refresh, setActions }`. `refresh()` re-fetches the summary AND calls the shell's badge refetch (AdminLayout's `fetchBadges`, exposed through its existing outlet context alongside `badges`; today it is only on a 60s interval and the visibility handler), so the sidebar badge and the hub tab badge never disagree after a confirm or an approval. Rendering is never gated on the fetch: children mount immediately and the subtitle and counts appear when the data arrives. While loading, the count and badge slots are empty, not zero.
- **Page actions slot:** Outlet context flows parent → child, so the child registers its header actions. `setActions(node | null)` is called by the child in an effect on mount and cleared on unmount; the layout renders whatever is registered in `.page-actions`. The child owns the modal the action opens (Reviews' manual-log form, Roster's Send SMS link). No lifted modal state in the layout.
- **Routes in `App.js`:** `/staffing` element `StaffHubLayout`, index → Roster, `hiring` → Hiring, `payroll` → Payroll, `reviews` → Reviews. **The three admin-only children are wrapped in `<ProtectedRoute adminStrict>`** (the Marketing precedent at `App.js:644`), because hiding a tab is not a guard: a manager reaching `/staffing/payroll` by URL, bookmark or the new redirects must bounce at the route, not land on a page where every fetch 403s. The three existing `/staffing/*` detail routes stay as siblings outside the layout.
- **Children drop their own `.page-header`.** The hub owns the title. Each child renders its toolbar and content directly under the tabs.
- **Hub tab chrome per child:** Roster shows `.hub-tab-count` = `active_count`. Hiring shows `.hub-tab-badge` = `new_applications` when > 0. Payroll shows nothing (no badge in v1). Reviews shows `.hub-tab-badge` = `pending_reviews` when > 0. Counts are ambient; badges mean a decision is waiting.
- **The live subtitle:** `{active_count} active · pay run {Mon D} to {D} {status word}, payday {Dow Mon D} · {pending_reviews} review(s) to confirm`, with `nothing to confirm` at zero and `No active staff yet` at zero active. The status word is `open` when the derived period has no row yet or its row is `open`, and the row's own status (`processing`, `reopened`, `paid`) otherwise, so the subtitle never says "open" about a week that is mid-process. The pay-run clause derives its window from today's Chicago date (§5), so a quiet week still names the period; the "nothing accrued yet" state lives on the Payroll pay-run card (§7), not in the subtitle.
- **Managers.** Hiring, Payroll, Reviews and the Tips ledger APIs are `adminOnly` (`applications.js`, `hiring.js`, `payroll*.js`, `staffReviews*.js`, and the `/tips`, `/tip-feedback` routes in `contractorTipPage.js`; the contractor tip-page mutations in that same file are `requireAdminOrManager`, which is why §9 gates by role rather than by file). A manager sees the hub with the Roster child only: the `.hub-tabs` strip is hidden when a single child is visible, the subtitle is `{active_count} active` alone, and the summary returns the admin-only fields as `null` for managers. `GET /admin/active-staff` additionally gates managers on `can_staff`; the summary applies the same rule, so a manager without `can_staff` gets every count as `null`, the subtitle is empty, and the Roster child shows its existing 403 error state rather than a headcount for a roster they cannot read.

## 5. Server

All reads. One new route file, one roster-feed fix, two projection extensions, one parameter extension. **Review scaling, stated honestly:** `scripts/sensitive-match.js` matches only `payroll.js` among the files this spec touches; `contractorTipPage.js`, `staffReviews.js`, `staffReviewsContest.js`, `dutyLines.js` and the new `staffHub.js` are NOT on `scripts/sensitive-paths.txt`. This spec adds `server/utils/dutyLines.js` (the bounty money writer) and `server/routes/admin/contractorTipPage.js` (tip money reads and tip-page mutations) to the list in the server lane, and the server lane runs the full fleet explicitly regardless.

- **`GET /api/admin/staff-hub/summary`** (new, `server/routes/admin/staffHub.js`, mounted from `server/routes/admin/index.js`, `auth` + `requireAdminOrManager`). Returns:
  ```
  { active_count, deactivated_count, former_staff_count, imported_count,
    new_applications, pending_reviews,
    open_period: { start_date, end_date, payday, exists, status, payouts_accrued } }
  ```
  - **Counts use the roster feed's own predicate**, including its `onboarding_completed = true` condition for the active set (see the roster-feed fix below for the deactivated set), and every count is bounded to `role IN ('staff','manager')` so admin and client rows never fall into a staff figure. `active_count` = status approved, the same set the Roster's Active tab shows (the client stops filtering `approved` on its own; the server's set is the one truth). `deactivated_count` = status deactivated; `imported_count` = deactivated AND (`cc_id LIKE 'legacy_cc:%' OR import_source = 'payment_history_import'`); `former_staff_count` = deactivated minus imported. Four numbers, one predicate family, one screen.
  - `new_applications` = the badge-counts predicate verbatim. `pending_reviews` = `staff_reviews WHERE status = 'pending'` (any star count; it counts decisions waiting, not dollars).
  - **`open_period` is derived, not read:** `chicagoTodayYmd()` from `server/utils/businessTime.js` (never `new Date()`; the late-evening UTC drift is a documented defect class) into `payPeriodForDate` + `computePayday` from `server/utils/payrollPeriods.js` gives the window; a LEFT JOIN to `pay_periods ON start_date = $1` (UNIQUE, never a `BETWEEN`) fills `exists`, `status` and `payouts_accrued` (count of `payouts` for that period id), all `false`/`null`/0 when the row is not there yet. Rows are created lazily by `ensurePayPeriod` when the first shift accrues (usually Saturday), so on a Wednesday the row does not exist and the subtitle must not go blank or fall back to last week. **This endpoint never writes:** it must not adopt the `INSERT INTO pay_periods` fallback that `payrollLateTip.js` and `payrollClawback.js` wrap around `findOpenPeriodForDate`.
  - For managers, `new_applications`, `pending_reviews` and `open_period` are `null` (the subtitle logic treats `null` and 0 alike; badge-counts keeps its own `0` convention and the Sidebar's `|| 0` tolerates both). For a manager without `can_staff`, the four counts are `null` too.
- **Roster feed fix.** `GET /admin/active-staff?include_stubs=true` INNER JOINs `onboarding_progress` and requires `onboarding_completed = true`, which is right for the active set and wrong for the deactivated set: the nine payment-history placeholders were deliberately left without a progress row, so today's "All" tab cannot show them and §6's "Imported records · 9" group would render empty. The feed becomes `LEFT JOIN onboarding_progress` with the completion condition applied only to non-deactivated statuses (`u.onboarding_status = 'deactivated' OR op.onboarding_completed = true`). The active set is unchanged byte-for-byte; `users.activeStaff.test.js` gets the deactivated-without-progress case. The roster also sends `limit=100` (the endpoint max) and, when `total > 100`, renders a "Showing 100 of {total}" line with a page control, so group counts in the table come from the same universe as the hub counts.
- **`GET /api/admin/badge-counts`** adds `pending_reviews` (same predicate), zeroed for managers exactly as `new_applications` is.
- **`GET /api/admin/tips`** gains no join. The ledger's Status column (§7) derives from columns already on the row; the endpoint adds `shift_id`, `deferred_at`, `rolled_forward_at`, `refunded_amount_cents`, `dispute_won_at` to its projection. Existing filters (`bartender_id`, `from`, `to`, cursor, `limit` 50) unchanged.
- **`GET /api/admin/tip-feedback`** accepts an optional `target_user_id` filter, validated with `Number.isInteger` (reject otherwise; do not copy the sibling `bartender_id` filter, which pushes a bare `parseInt` and 500s on garbage). Stays `adminOnly`.
- **`GET /api/admin/staff-reviews`** adds `bounty_cents: REVIEW_BOUNTY_CENTS` and `bounties_paid_cents` (SUM of `payout_duty_lines.amount_cents WHERE kind='review_bounty'`) and `total_logged` (COUNT of `staff_reviews`) to its response envelope, so no page ever embeds the bounty figure and the footer totals are not capped by the list's `LIST_LIMIT`.

No schema changes. No writes.
